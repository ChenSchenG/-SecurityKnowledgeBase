A04:2021 - 不安全设计 (Insecure Design)

HIGH 排名第4 (新增)

Insecure Design 是 2021 年新增的分类。它关注的不是实现层面的 bug，而是设计和架构层面的缺陷。即使代码写得完美无缺，如果设计本身有安全漏洞，系统仍然是脆弱的。

不安全设计 vs 不安全实现

不安全设计：设计阶段就缺失安全控制。例如"密码找回功能设计为仅通过安全问题验证"——无论代码如何实现，安全问题本身就容易被社工猜出。

不安全实现：设计正确但代码实现有 bug。例如设计要求密码哈希存储，但开发者用了 MD5。

不安全的设计无法通过完美的实现来修复——你需要重新设计。

1. 概述与核心概念

1.1 为什么设计阶段如此重要

修复成本随阶段指数增长： 阶段 相对成本 修复难度 ───────────────────────────────────────── 需求阶段 1x 修改文档 设计阶段 5x 修改架构图 编码阶段 10x 修改代码+测试 测试阶段 20x 回归+修改+再测试 上线后 100x 紧急补丁+事故响应+声誉损失 结论：安全必须"左移"(Shift Left) 越早发现设计缺陷，修复成本越低

1.2 不安全设计的典型表现

类别不安全设计示例正确做法
业务逻辑优惠券无使用次数限制设计时定义使用限制和互斥规则
认证设计密码找回仅用安全问题多因素验证 + 邮件/短信验证码
数据流客户端决定商品价格价格由服务端计算，客户端仅提交数量
信任边界信任所有内网请求零信任架构，内网也需认证
速率控制无限制的 API 调用Rate Limiting + 防滥用机制
错误处理异常时回退到无认证模式Fail Secure - 异常时拒绝访问

2. 威胁建模 (Threat Modeling)

威胁建模是在设计阶段系统性地识别和评估安全威胁的方法。它是防止不安全设计的最重要手段。

3. 安全设计原则

3.1 核心设计原则

安全设计十大原则
  1. 最小权限 (Least Privilege)：只给予完成任务所需的最少权限
  2. 纵深防御 (Defense in Depth)：多层安全控制，一层失败不致系统沦陷
  3. 安全默认 (Secure Defaults)：默认配置应该是安全的
  4. 失败安全 (Fail Secure)：异常时拒绝访问，而非允许
  5. 不信任任何输入 (Zero Trust Input)：所有外部数据都视为恶意
  6. 职责分离 (Separation of Duties)：关键操作需要多人/多步骤确认
  7. 保持简洁 (Keep It Simple)：复杂系统更容易出错
  8. 开放设计 (Open Design)：安全性不依赖于设计的保密（Kerckhoffs原则）
  9. 完全中介 (Complete Mediation)：每次访问都检查权限，不依赖缓存
  10. 心理可接受性 (Psychological Acceptability)：安全机制不应让用户体验过差

3.2 Fail Secure vs Fail Open

# ❌ Fail Open - 认证服务宕机时允许所有请求
def authenticate(request):
    try:
        result = auth_service.verify(request.token)
        return result.is_valid
    except AuthServiceUnavailable:
        # 认证服务挂了，先放行吧...
        logger.warning("Auth service down, allowing request")
        return True  # 危险！攻击者可以故意打垮认证服务

# ✅ Fail Secure - 认证服务宕机时拒绝所有请求
def authenticate(request):
    try:
        result = auth_service.verify(request.token)
        return result.is_valid
    except AuthServiceUnavailable:
        # 认证服务挂了，安全起见拒绝访问
        logger.critical("Auth service down, denying all requests")
        raise ServiceUnavailableError("Please try again later")

# ❌ Fail Open - 防火墙规则异常时放行
# iptables 默认 policy ACCEPT + 规则加载失败 = 无防护
#
# ✅ Fail Secure - 防火墙默认拒绝
# iptables -P INPUT DROP   ← 默认拒绝
# iptables -P FORWARD DROP

4. 滥用案例 (Abuse Cases)

传统的 Use Case 描述系统"应该怎么用"。Abuse Case 描述系统"会被怎么滥用"。安全设计要求同时考虑两者。

4.1 User Story vs Abuse Story

User Story (正常)Abuse Story (攻击)安全需求
用户可以注册账户攻击者批量注册垃圾账户CAPTCHA、邮箱验证、速率限制
用户可以找回密码攻击者枚举有效用户名统一响应消息、不透露账号是否存在
用户可以使用优惠券攻击者重复使用同一优惠券幂等性设计、使用后标记
用户可以评价商品竞争对手刷差评购买验证、异常行为检测
用户可以转账利用竞态条件双重花费原子操作、分布式锁
用户可以下载文件攻击者下载未授权文件间接引用、权限校验

5.2 价格篡改 (Price Manipulation)

# 前端代码
fetch('/api/order', {
    method: 'POST',
    body: JSON.stringify({

        quantity: 1,

# 攻击者修改请求
{

# ✅ 安全设计：服务端计算价格
@app.route('/api/order', methods=['POST'])
def create_order():
    data = request.json
    product = Product.query.get(data['product_id'])

    # 价格从数据库获取，不信任客户端
    unit_price = product.current_price
    quantity = data['quantity']

    # 服务端计算总价
    total = unit_price * quantity

    # 应用优惠（服务端验证优惠规则）
    discount = calculate_discount(current_user, product, quantity)
    final_price = total - discount

    if final_price <= 0:
        abort(400, "Invalid price calculation")

    order = Order(
        user_id=current_user.id,
        product_id=product.id,
        quantity=quantity,
        unit_price=unit_price,
        total_price=final_price

    db.session.add(order)
    db.session.commit()

5.3 流程绕过 (Process Bypass)

多步骤流程绕过攻击： 正常购物流程： Step1: 选商品 → Step2: 填地址 → Step3: 支付 → Step4: 完成 攻击：直接请求 Step4 的接口 POST /api/order/complete {"order_id": "ORD-12345"} → 如果后端不验证前置步骤是否完成 → 免费拿货！ 防御设计：状态机模型 ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ │ CART │───→│ADDRESS│───→│ PAID │───→│SHIPPED│ └──────┘ └──────┘ └──────┘ └──────┘ ↑ │ │ └───────────┘ │ (只有PAID状态才能发货) (可回退) ↓ ┌──────────┐ │COMPLETED │ └──────────┘ 每个状态转换都验证： 1. 当前状态是否允许此转换？ 2. 前置条件是否满足？ 3. 操作人是否有权限？
# ✅ 状态机设计 - 防止流程绕过
class OrderStateMachine:
    TRANSITIONS = {
        'cart':      ['address'],        # cart 只能到 address
        'address':   ['payment', 'cart'], # address 可到 payment 或回退
        'payment':   ['paid'],           # payment 只能到 paid
        'paid':      ['shipped'],        # paid 只能到 shipped
        'shipped':   ['completed'],      # shipped 只能到 completed
    }

    @staticmethod
    def can_transition(order, target_state):
        current = order.state
        allowed = OrderStateMachine.TRANSITIONS.get(current, [])
        return target_state in allowed

    @staticmethod
    def transition(order, target_state):
        if not OrderStateMachine.can_transition(order, target_state):
            raise InvalidStateTransition(
                f"Cannot move from '{order.state}' to '{target_state}'"
            )
        # 验证前置条件
        if target_state == 'shipped' and not order.payment_confirmed:
            raise PreconditionFailed("Payment not confirmed")
        order.state = target_state
        order.state_history.append({
            'from': order.state,
            'to': target_state,
            'timestamp': datetime.now(),
            'actor': current_user.id
        })

5.4 数值操纵 (Numeric Manipulation)

# ❌ 负数转账攻击
POST /api/transfer
{
    "from": "attacker_account",
    "to": "victim_account",
    "amount": -1000  // 负数！相当于从对方账户转钱到自己
}

# 后端代码（漏洞）
def transfer(from_acc, to_acc, amount):
    from_acc.balance -= amount    # 减去-1000 = 加1000
    to_acc.balance += amount      # 加上-1000 = 减1000
    # 攻击者余额增加，受害者余额减少！

# ✅ 安全设计：严格验证数值
def transfer(from_acc, to_acc, amount):
    # 类型检查
    if not isinstance(amount, (int, float)):
        raise ValueError("Amount must be numeric")

    # 范围检查
    if amount <= 0:
        raise ValueError("Amount must be positive")

    if amount > MAX_TRANSFER_LIMIT:
        raise ValueError("Exceeds transfer limit")

    # 精度检查（防止浮点数精度攻击）
    amount = Decimal(str(amount)).quantize(Decimal('0.01'))

    # 余额检查
    if from_acc.balance < amount:
        raise InsufficientFunds()

    # 原子操作
    with db.atomic():
        from_acc.balance -= amount
        to_acc.balance += amount

6. 真实攻击场景

6.1 场景一：验证码绕过 (OTP Bypass)

案例：某电商平台手机验证码绕过

设计缺陷：验证码验证接口在验证成功后，没有将验证码标记为已使用。

攻击步骤：

  1. 请求发送验证码到自己手机
  2. 正确输入验证码，验证成功
  3. 拦截"验证成功"的响应，但不继续下一步
  4. 修改手机号为受害者号码，重放验证成功的请求
  5. 系统认为受害者手机已验证 → 接管账户
# 安全设计要求：
# 1. 验证码与手机号绑定
# 2. 验证码使用后立即失效
# 3. 验证结果与后续操作通过 server-side session 关联

class OTPVerification:
    def verify(self, phone, code, purpose):
        stored = redis.get(f"otp:{phone}:{purpose}")
        if not stored or stored != code:
            return False

        # 验证成功后立即删除（一次性使用）
        redis.delete(f"otp:{phone}:{purpose}")

        # 在 session 中记录验证结果（不依赖客户端）
        session[f'verified_{purpose}'] = {
            'phone': phone,
            'timestamp': time.time(),
            'expires': time.time() + 300  # 5分钟有效
        }
        return True

    def is_verified(self, purpose, expected_phone):
        verification = session.get(f'verified_{purpose}')
        if not verification:
            return False
        if verification['phone'] != expected_phone:
            return False  # 手机号不匹配
        if time.time() > verification['expires']:
            return False  # 已过期
        return True

6.2 场景二：无限优惠券 (Coupon Abuse)

# 攻击场景：优惠券系统设计缺陷

# 缺陷1：优惠券使用无幂等性检查
# 同一订单多次提交优惠券请求 → 多次扣减

# 缺陷2：优惠券金额可超过订单金额
# 100元商品使用200元优惠券 → 退款100元到余额

# 缺陷3：优惠券可在取消订单后复用
# 下单使用优惠券 → 取消订单 → 优惠券恢复 → 已获得的优惠保留

# ✅ 安全设计
class CouponSystem:
    def apply_coupon(self, order, coupon_code):
        coupon = Coupon.query.filter_by(code=coupon_code).first()

        # 检查1：优惠券是否存在和有效
        if not coupon or coupon.status != 'active':
            raise InvalidCoupon()

        # 检查2：是否过期
        if coupon.expires_at < datetime.now():
            raise CouponExpired()

        # 检查3：是否已被使用（幂等性）
        if coupon.used_by_order_id is not None:
            raise CouponAlreadyUsed()

        # 检查4：使用条件（最低消费等）
        if order.subtotal < coupon.min_order_amount:
            raise MinAmountNotMet()

        # 检查5：折扣金额不能超过订单金额
        discount = min(coupon.discount_amount, order.subtotal)

        # 检查6：用户限制（每人限用一次等）
        if CouponUsage.query.filter_by(
            user_id=current_user.id, coupon_type=coupon.type
        ).count() >= coupon.per_user_limit:
            raise CouponLimitReached()

        # 原子操作：标记使用
        with db.atomic():
            coupon.status = 'used'
            coupon.used_by_order_id = order.id
            coupon.used_at = datetime.now()
            order.discount = discount
            order.total = order.subtotal - discount

6.3 场景三：投票/抽奖系统滥用

7.2 安全需求清单 (基于 OWASP ASVS)

# OWASP ASVS (Application Security Verification Standard) 核心章节

V1: 架构、设计和威胁建模
  □ 所有组件已识别并有明确的安全需求
  □ 已进行威胁建模
  □ 所有数据流已标识并有安全控制

V2: 认证
  □ 密码策略: 最少8字符，支持64+字符
  □ 防暴力破解: 账户锁定或渐进延迟
  □ 凭证安全存储: bcrypt/scrypt/Argon2

V3: 会话管理
  □ Session ID 足够随机（至少128bit熵）
  □ 登出后 Session 立即失效
  □ 空闲超时和绝对超时

V4: 访问控制
  □ 默认拒绝原则
  □ 所有数据访问都验证归属
  □ 管理功能有独立的权限验证

V5: 输入验证
  □ 所有输入在服务端验证
  □ 使用参数化查询
  □ 输出编码防止注入

V13: API 安全
  □ API 有认证和授权
  □ 速率限制
  □ 输入大小限制
