A01:2021 - 权限控制失效

CRITICAL 排名第1

Broken Access Control 从 2017 年的第 5 位上升到 2021 年的第 1 位。94% 的应用都被测试出存在某种形式的权限控制失效。这不是某个单一漏洞，而是一整类问题的总称。

核心概念

访问控制强制执行策略，使用户不能在超出其预期权限范围外进行操作。失效通常导致：未授权信息泄露、数据篡改或删除、执行超出权限的业务功能。

1. 权限控制基础

1.1 认证 vs 授权

概念英文回答的问题对应机制
认证Authentication (AuthN)你是谁？密码、MFA、证书
授权Authorization (AuthZ)你能做什么？ACL、RBAC、ABAC
审计Auditing你做了什么？日志系统

权限控制失效 = 授权（Authorization）环节出了问题。用户已经通过认证（登录成功），但能访问或操作不属于自己权限范围的资源。

1.2 权限控制模型

模型全称原理适用场景
DACDiscretionary Access Control资源拥有者自行决定谁能访问文件系统(Linux chmod)
MACMandatory Access Control系统强制执行，用户不能更改军事系统, SELinux
RBACRole-Based Access Control基于角色分配权限大多数Web应用
ABACAttribute-Based Access Control基于属性（时间/地点/部门等）动态决策复杂企业系统
RBAC 模型示意： 用户 ──分配──→ 角色 ──拥有──→ 权限 示例： 用户Alice ──→ 普通用户角色 ──→ [查看自己订单, 修改个人信息] 用户Bob ──→ 管理员角色 ──→ [查看所有订单, 修改用户信息, 删除用户] 权限控制失效场景： Alice 通过修改请求参数，执行了"管理员角色"才有的权限 Alice 通过修改URL中的ID，查看了 Bob 的订单

2. 水平越权（Horizontal Privilege Escalation）

定义：同级别用户 A 访问了用户 B 的数据。两者权限等级相同，但数据归属不同。

2.1 典型场景

正常请求： GET /api/orders/1001 (Alice的订单) Cookie: session=alice_session_token 攻击：Alice 修改订单ID GET /api/orders/1002 (Bob的订单!) Cookie: session=alice_session_token 如果后端代码： order = db.query("SELECT * FROM orders WHERE id = ?", order_id) return order // ← 没有验证 order.user_id == current_user.id → Alice 就能看到 Bob 的订单详情（包括地址、手机号等敏感信息）

2.2 漏洞代码 vs 安全代码

# ❌ 漏洞代码 - 没有检查数据归属
@app.route('/api/orders/<int:order_id>')
@login_required
def get_order(order_id):
    order = Order.query.get(order_id)  # 只按ID查
    if not order:
        return {"error": "Not found"}, 404
    return order.to_dict()  # 直接返回，没验证归属！

# ✅ 安全代码 - 验证数据归属权
@app.route('/api/orders/<int:order_id>')
@login_required
def get_order(order_id):
    order = Order.query.get(order_id)
    if not order:
        return {"error": "Not found"}, 404
    if order.user_id != current_user.id:  # ← 关键检查
        return {"error": "Forbidden"}, 403
    return order.to_dict()

2.3 水平越权的常见触发点

  • URL 路径中的 ID：/profile/123 → /profile/124
  • 查询参数：?user_id=123 → ?user_id=124
  • POST 请求体：{"orderId": "1001"} → {"orderId": "1002"}
  • Cookie/Header 中的标识：X-User-Id: 123（如果后端信任前端传来的ID）
  • 文件名/路径：/files/user123/document.pdf → /files/user124/document.pdf

3. 垂直越权（Vertical Privilege Escalation）

定义：低权限用户执行了高权限用户才有的操作。例如普通用户执行管理员功能。

3.1 典型场景

管理后台： 正常：admin 访问 /admin/users/delete?id=5 → 删除用户 攻击：普通用户直接访问 /admin/users/delete?id=5 如果后端只靠"这个URL在管理员菜单里显示"来保护 → 攻击者直接输入URL即可绕过！ 前端隐藏 ≠ 后端保护！ 常见错误思维： "这个按钮只有管理员界面才显示，普通用户看不到" "前端已经判断了角色，后端不需要再判断" → 大错特错！攻击者不通过你的前端界面发请求！

3.2 真实案例模式

# ❌ 漏洞代码 - 只在前端隐藏管理功能
# 后端没有任何权限验证
@app.route('/admin/users', methods=['DELETE'])
@login_required  # 只验证了登录，没验证角色！
def delete_user():
    user_id = request.json['user_id']
    User.query.filter_by(id=user_id).delete()
    db.session.commit()
    return {"message": "User deleted"}

# ✅ 安全代码 - 后端强制验证角色
@app.route('/admin/users', methods=['DELETE'])
@login_required
@require_role('admin')  # ← 装饰器验证角色
def delete_user():
    user_id = request.json['user_id']
    User.query.filter_by(id=user_id).delete()
    db.session.commit()
    return {"message": "User deleted"}

# 权限装饰器实现
def require_role(role):
    def decorator(f):
        @wraps(f)
        def wrapper(*args, **kwargs):
            if current_user.role != role:
                abort(403)  # Forbidden
            return f(*args, **kwargs)
        return wrapper
    return decorator

4. IDOR - 不安全的直接对象引用

IDOR (Insecure Direct Object Reference) 是水平越权和垂直越权的具体表现形式之一。当应用使用用户可控的输入直接引用内部对象（数据库记录、文件等）时，就可能存在 IDOR。

4.1 IDOR 的各种表现

位置漏洞URL/请求攻击方式
URL 路径GET /api/invoices/INV-001遍历: INV-002, INV-003...
查询参数GET /download?file_id=85修改: file_id=86, 87...
POST 请求体POST /transfer {"to_account": "A123"}修改目标账户
HTTP HeaderX-Company-Id: 100修改为其他公司ID
文件路径GET /files/reports/2024/q1.pdf修改路径查看其他文件

4.2 IDOR 挖掘技巧

渗透测试中如何找 IDOR
  1. 注册两个账户（A和B），分别操作，记录所有涉及ID的请求
  2. 交叉测试：用 A 的身份请求 B 的资源ID
  3. 关注所有数字/字符串ID：订单号、用户ID、文件名、UUID
  4. 检查 API 文档：有时候文档会暴露内部ID格式
  5. 尝试预测规律：连续数字？Base64编码？UUID是否真的随机？
  6. 检查批量操作接口：/api/users?ids=1,2,3,4,5

4.3 IDOR 防御

  • 服务端验证归属：每次访问都验证 resource.owner == current_user
  • 使用间接引用：不暴露数据库ID，使用 session-specific 映射
  • UUID 代替自增ID：增加遍历难度（但不能替代权限检查！）
  • 统一权限层：在框架层面强制所有查询都带权限过滤
# 间接引用示例：用户只看到映射后的ID
user_files_map = {}  # session中存储

@app.route('/list-files')
@login_required
def list_files():
    files = File.query.filter_by(owner=current_user.id).all()
    # 为每个文件生成临时引用ID（只在当前session有效）
    session['file_map'] = {str(i): f.id for i, f in enumerate(files)}
    return [{"ref": str(i), "name": f.name} for i, f in enumerate(files)]

@app.route('/download/<ref>')
@login_required
def download(ref):
    file_map = session.get('file_map', {})
    real_id = file_map.get(ref)
    if not real_id:
        abort(404)
    # 即使用了间接引用，仍然验证归属
    file = File.query.get(real_id)
    if file.owner != current_user.id:
        abort(403)
    return send_file(file.path)

5. 目录遍历（Path Traversal）

通过操纵文件路径参数，访问服务器上的任意文件。也称为 Directory Traversal 或 Dot-Dot-Slash 攻击。

5.1 攻击原理

# 正常请求
GET /download?file=report.pdf
→ 服务器读取 /var/www/files/report.pdf

# 攻击请求
GET /download?file=../../../etc/passwd
→ 服务器读取 /var/www/files/../../../etc/passwd
→ 实际读取 /etc/passwd !

5.2 绕过技术

防御措施绕过方法示例
过滤 ../双写绕过....//....//etc/passwd
过滤 ../URL 编码%2e%2e%2f 或 %252e%252e%252f
限制文件后缀Null 字节截断(旧版PHP)../etc/passwd%00.pdf
Linux 路径绝对路径/etc/passwd
替换为空嵌套绕过..././..././ → 替换后变成 ../../

5.3 安全防御

import os

# ✅ 安全的文件访问实现
ALLOWED_BASE = '/var/www/files'

def safe_read_file(filename):
    # 1. 规范化路径（解析 ../ 和符号链接）
    full_path = os.path.realpath(os.path.join(ALLOWED_BASE, filename))

    # 2. 验证结果路径是否仍在允许的目录下
    if not full_path.startswith(ALLOWED_BASE):
        raise PermissionError("Path traversal detected!")

    # 3. 检查文件是否存在
    if not os.path.isfile(full_path):
        raise FileNotFoundError("File not found")

    return open(full_path, 'rb').read()

访问未被链接但实际存在的页面或文件。通过猜测或暴力枚举 URL 发现隐藏的管理页面、备份文件、配置文件等。

7. HTTP 方法绕过

有些权限控制只检查特定 HTTP 方法，攻击者通过使用不同的方法绕过限制。

场景：WAF/代码只拦截 POST 请求的参数 正常请求被拦截： POST /admin/deleteUser HTTP/1.1 → WAF: 检测到敏感操作，拦截！ 绕过尝试： GET /admin/deleteUser?id=5 ← 方法更改 PUT /admin/deleteUser ← 方法更改 POST /admin/deleteUser HTTP/1.1 X-HTTP-Method-Override: PUT ← 方法覆盖头 POST /admin/deleteUser HTTP/1.1 Content-Type: application/json ← Content-Type变更 {"_method": "DELETE", "id": 5} ← 框架级方法覆盖

常见方法覆盖技巧

# HTTP 方法覆盖头（很多框架支持）
X-HTTP-Method: DELETE
X-HTTP-Method-Override: PUT
X-Method-Override: PATCH

# URL 参数覆盖
POST /api/users/5?_method=DELETE

# 利用 TRACE 方法泄露信息
TRACE / HTTP/1.1
→ 服务器回显请求（可能包含认证Cookie）

8. JWT 相关权限漏洞

JSON Web Token (JWT) 是现代 Web 应用最常用的认证/授权机制之一。但如果实现不当，会导致严重的权限问题。

8.1 JWT 结构

JWT = Header.Payload.Signature eyJhbGciOiJIUzI1NiJ9.eyJ1c2VyIjoiYWxpY2UiLCJyb2xlIjoidXNlciJ9.xxxxx |_____________________| |_________________________________________| |_____| Header Payload Signature (Base64) (Base64) (Base64) Header: {"alg": "HS256", "typ": "JWT"} Payload: {"user": "alice", "role": "user", "exp": 1700000000} Signature: HMAC-SHA256(base64(header) + "." + base64(payload), secret)

8.2 JWT 常见漏洞

漏洞1：alg=none 攻击

# 原始token (HS256签名)
# Header: {"alg": "HS256"}
# Payload: {"user": "alice", "role": "user"}

# 攻击：将算法改为 none，去掉签名
import base64, json

header = base64.urlsafe_b64encode(
    json.dumps({"alg": "none", "typ": "JWT"}).encode()
).rstrip(b'=')

payload = base64.urlsafe_b64encode(
    json.dumps({"user": "alice", "role": "admin"}).encode()  # 提权!
).rstrip(b'=')

# 无签名的token（末尾加点）
forged_token = f"{header.decode()}.{payload.decode()}."

# 如果服务端接受 alg=none → 权限提升成功！

漏洞2：将 RS256 改为 HS256

# 正常：服务端用 RSA 私钥签名，用公钥验证
# 攻击：把 alg 改成 HS256，用 RSA 公钥作为 HMAC 密钥签名
# 如果服务端逻辑是：
#   key = get_key()  # 获取公钥
#   if header.alg == "HS256":
#       verify_hmac(token, key)  # 用公钥当HMAC密钥验证！
# → 攻击者知道公钥，可以用公钥签名伪造token！

# 防御：验证时固定算法，不信任 header 中的 alg
import jwt
# ✅ 正确做法：强制指定算法
decoded = jwt.decode(token, public_key, algorithms=["RS256"])

漏洞3：弱密钥暴力破解

# 如果 HMAC 密钥太短/太简单，可以暴力破解
# 工具: hashcat, jwt_tool

# hashcat 破解 JWT 密钥
hashcat -m 16500 jwt.txt wordlist.txt

# jwt_tool 测试各种JWT漏洞
python3 jwt_tool.py $TOKEN -C -d wordlist.txt  # 字典攻击
python3 jwt_tool.py $TOKEN -X a               # alg=none 测试
python3 jwt_tool.py $TOKEN -X k               # key confusion 测试

漏洞4：token 未验证过期时间

# Payload 中的 exp 字段表示过期时间
# 如果服务端不检查 exp → token 永不过期 → 泄露后永久可用

# ✅ 正确验证
decoded = jwt.decode(token, secret, algorithms=["HS256"],
                     options={"verify_exp": True})  # 默认就会验证

9. 竞态条件与权限

TOCTOU (Time of Check to Time of Use) 漏洞：权限检查和实际操作之间存在时间差，攻击者在这个窗口期修改条件。

TOCTOU 竞态条件： 正常流程： 1. 检查用户余额: balance >= 100 ✓ 2. 扣除余额: balance -= 100 3. 发放商品 攻击：同时发送两个请求 线程1: 检查余额(100 >= 100 ✓) → 还没扣款 线程2: 检查余额(100 >= 100 ✓) → 还没扣款 线程1: 扣款(balance = 0) → 发货 线程2: 扣款(balance = -100) → 发货 ← 双重消费！ 同理用于优惠券、积分兑换、投票等场景
# ❌ 存在竞态条件的代码
@app.route('/transfer', methods=['POST'])
def transfer():
    amount = request.json['amount']
    # TOCTOU: 检查和操作不是原子的
    if current_user.balance >= amount:  # 检查
        time.sleep(0.01)  # 模拟处理延迟
        current_user.balance -= amount   # 操作
        target.balance += amount
        db.session.commit()

# ✅ 使用数据库锁保证原子性
@app.route('/transfer', methods=['POST'])
def transfer():
    amount = request.json['amount']
    # 使用 SELECT FOR UPDATE 加行锁
    user = User.query.with_for_update().get(current_user.id)
    if user.balance >= amount:
        user.balance -= amount
        target = User.query.with_for_update().get(target_id)
        target.balance += amount
        db.session.commit()
    else:
        abort(400, "Insufficient balance")

10. 系统性防御方案

10.1 防御原则

权限控制设计原则
  1. 默认拒绝（Deny by Default）：除非明确允许，否则拒绝一切访问
  2. 最小权限原则：只给予完成任务所需的最小权限
  3. 服务端强制检查：永远不信任客户端的权限判断
  4. 统一权限层：在一个地方集中处理权限，而非散落各处
  5. 纵深防御：多层检查，任何一层失败都能阻止攻击

10.2 实现模式

# 方案1：中间件统一权限检查（推荐）
class PermissionMiddleware:
    """所有请求经过统一权限检查"""

    # 权限矩阵：path pattern → required role
    RULES = [
        (r'/admin/.*', ['admin']),
        (r'/api/users/\d+/orders', ['admin', 'self']),  # self=只能访问自己的
        (r'/api/.*', ['user', 'admin']),
    ]

    def process_request(self, request):
        for pattern, roles in self.RULES:
            if re.match(pattern, request.path):
                if not self.check_permission(request.user, roles, request):
                    return Response(status=403)
        return None

# 方案2：装饰器模式
from functools import wraps

def require_permission(*permissions):
    def decorator(f):
        @wraps(f)
        def wrapper(*args, **kwargs):
            for perm in permissions:
                if not current_user.has_permission(perm):
                    abort(403)
            return f(*args, **kwargs)
        return wrapper
    return decorator

@app.route('/api/reports/<int:report_id>')
@login_required
@require_permission('view_reports')
@require_ownership('report_id', Report)  # 自定义：验证资源归属
def get_report(report_id):
    ...

# 方案3：查询级别过滤（最彻底）
class SecureQuery:
    """所有数据库查询自动加上权限过滤"""

    @staticmethod
    def get_user_orders(user):
        # 查询本身就包含权限约束
        return Order.query.filter_by(user_id=user.id)

    @staticmethod
    def get_all_orders(user):
        if user.role != 'admin':
            raise PermissionError()
        return Order.query.all()

10.3 检查清单

检查项说明
是否所有 API 都有权限检查？包括 GET/POST/PUT/DELETE 所有方法
是否验证了数据归属？不仅检查角色，还要检查"这条数据是你的吗"
ID 是否可预测/可遍历？使用 UUID 增加难度（但不替代权限检查）
管理功能是否有后端保护？不能仅靠前端隐藏
是否有速率限制？防止批量遍历
是否记录了异常访问？权限拒绝应该触发告警
是否有自动化测试？权限矩阵应该有对应的测试用例

10.4 Burp Suite 测试权限的实战流程

使用 Burp Suite 测试权限控制： 1. 配置两个账户的 Session - 账户A (普通用户): 使用 Session 1 - 账户B (管理员): 使用 Session 2 2. 用账户B正常操作，记录所有请求 Burp Proxy → HTTP History 3. 将账户B的请求发送到 Repeater - 替换 Cookie/Token 为账户A的 - 观察响应 4. 使用 Autorize 插件自动化测试 - 配置低权限 Cookie - 自动对比每个请求在不同权限下的响应 - 标记可能存在越权的请求 5. 重点测试： □ 所有包含 ID 参数的接口 □ 管理后台的每个功能 □ 修改/删除操作 □ 文件下载/导出功能 □ 批量操作接口
真实世界案例
  • Facebook (2018)：通过修改 API 中的用户 ID，可以删除任意用户的照片
  • 某航空公司：修改订单号可查看他人机票信息（姓名、身份证、行程）
  • 某电商平台：修改优惠券ID可使用他人的大额优惠券
