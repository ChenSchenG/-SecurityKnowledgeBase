认证与授权机制 (Authentication & Authorization)

认证 (Authentication, AuthN) 回答"你是谁？"，授权 (Authorization, AuthZ) 回答"你能做什么？"。这两个机制是 Web 应用安全的核心支柱，也是攻击者最常瞄准的目标。

学习目标
  • 理解认证三因素和多因素认证的实现原理
  • 掌握 Session 和 Token 两种认证状态管理方式
  • 深入理解 JWT、OAuth 2.0、OpenID Connect 的工作流程
  • 掌握主流授权模型 (RBAC, ABAC) 的设计和实现
  • 识别认证授权系统的常见漏洞和防御手段
认证与授权的关系: ┌──────────────────────────────────────────────────────────────┐ │ 请求处理流程 │ ├──────────────────────────────────────────────────────────────┤ │ │ │ 用户请求 ──→ [认证 AuthN] ──→ [授权 AuthZ] ──→ 资源访问 │ │ "你是谁?" "你能做什么?" │ │ │ │ │ │ ▼ ▼ │ │ 身份验证失败 权限检查失败 │ │ HTTP 401 HTTP 403 │ │ Unauthorized Forbidden │ │ │ └──────────────────────────────────────────────────────────────┘ 关键区别: • 401 Unauthorized = 身份未验证 (实际是 "Unauthenticated") • 403 Forbidden = 身份已验证但无权限 (真正的 "Unauthorized")

1. 认证因素 (Authentication Factors)

认证因素是验证用户身份的不同类别方法。更多独立因素意味着更高的安全性。

因素类型描述示例攻击方式强度
Something You Know
(你知道的)		知识因素密码、PIN、安全问题钓鱼、暴力破解、社工低-中
Something You Have
(你拥有的)		持有因素手机、硬件 Token、智能卡物理盗窃、SIM Swap中-高
Something You Are
(你本身的)		生物因素指纹、面部、虹膜、声纹伪造生物特征、翻模高
Somewhere You Are
(你在哪)		位置因素IP 地理位置、GPSVPN、GPS 欺骗辅助
Something You Do
(你的行为)		行为因素打字节奏、鼠标移动模式模拟行为辅助
多因素 ≠ 多步骤

两个密码（密码 + 安全问题）仍然是单因素认证（都是"你知道的"）。真正的多因素认证必须结合不同类别的因素，例如：密码（知识）+ TOTP（持有）。

2. 密码认证 (Password-Based Authentication)

2.1 安全密码存储

密码存储演进: ⛔ Level 0: 明文存储 数据库: username | password alice | P@ssw0rd123 风险: 数据库泄露 → 所有密码暴露 ⛔ Level 1: 简单 Hash 数据库: username | hash alice | sha256("P@ssw0rd123") = a1b2c3... 风险: Rainbow Table 攻击, 相同密码产生相同 hash ⚠️ Level 2: Hash + Salt 数据库: username | salt | hash alice | x8k2m3p9 | sha256("x8k2m3p9" + "P@ssw0rd123") 风险: GPU 暴力破解仍然很快 (SHA-256 太快) ✅ Level 3: 专用密码哈希 (bcrypt/Argon2) 数据库: username | hash alice | $argon2id$v=19$m=65536,t=3,p=1$salt$hash 特点: 故意慢、抗 GPU、自带盐值

2.2 密码策略

策略传统做法 (已过时)现代最佳实践 (NIST 800-63B)
最小长度8 字符最少 8 字符，推荐 12+
复杂度要求必须含大小写+数字+符号不强制复杂度，鼓励长密码/passphrase
定期更换每 90 天强制更换不要求定期更换（除非有泄露证据）
禁用列表无检查是否在已泄露密码库中 (HaveIBeenPwned)
最大长度16 字符允许至少 64 字符
字符限制禁止特殊字符允许所有 Unicode 字符（含空格、emoji）
为什么 NIST 不再推荐复杂度要求？

研究表明，复杂度规则导致用户选择可预测的模式（如 Password1!）并写下密码。允许长 passphrase（如 "correct horse battery staple"）反而更安全且易记。结合泄露密码检查更有效。

3. 多因素认证 (Multi-Factor Authentication)

3.1 TOTP (Time-Based One-Time Password)

TOTP 工作原理 (RFC 6238): 注册阶段: ┌────────┐ ┌────────┐ │ 服务器 │───── 共享密钥 Secret ────→│ 用户App│ │ │ (通过 QR Code) │(Google │ │ │ │Authen.) │ └────────┘ └────────┘ 验证阶段: 服务器端: 用户端: TOTP = HMAC-SHA1(Secret, TOTP = HMAC-SHA1(Secret, floor(time/30)) floor(time/30)) = 取最后 6 位 = 取最后 6 位 = 847293 = 847293 用户输入 847293 → 服务器比对 → 通过 ✓ 关键参数: • 时间步长: 30 秒 (标准) • 位数: 6 位 (标准) 或 8 位 • 算法: HMAC-SHA1 / HMAC-SHA256 • 容差: 允许前后 1 个时间步长的偏差

3.2 FIDO2 / WebAuthn

WebAuthn — 抗钓鱼的认证标准

WebAuthn 是目前最安全的认证方式，因为它在协议层面防止钓鱼：

  • Origin 绑定：认证器会验证请求来源的 domain，伪造网站无法获取有效响应
  • 挑战-响应：基于公钥密码学，服务器从不接触私钥
  • 不可重放：每次认证包含唯一的 challenge
WebAuthn 认证流程: 注册 (Registration): ┌──────┐ ┌──────────┐ ┌──────────────┐ │浏览器 │←─ 1 ──│ 服务器 │ │ 认证器 │ │ │ challenge │ │(YubiKey/指纹) │ │ │──────────────────────────2──→│ │ │ │ 用户确认 (触摸/指纹) │ │ │ │←────────────────────────3───│ │ │ │ publicKey + credential ID │ 生成密钥对 │ │ │── 4 ──→│ │ │ 私钥不离开 │ │ │ attestation │ │ 认证器 │ └──────┘ └──────────┘ └──────────────┘ 认证 (Authentication): 1. 服务器发送 challenge + allowCredentials 2. 浏览器转发给认证器 (包含 origin 信息) 3. 认证器验证 origin + 用户确认 → 用私钥签名 challenge 4. 浏览器将签名返回服务器 5. 服务器用存储的公钥验证签名 为什么抗钓鱼: • 假网站 evil.com 请求认证 → 认证器检查 origin • origin = "evil.com" ≠ 注册时的 "bank.com" • 认证器拒绝签名 → 攻击失败

3.3 SMS OTP 的弱点

SMS 不是安全的第二因素

NIST 已将 SMS OTP 标记为"受限"验证方式。已知攻击：

  • SIM Swap：攻击者社工运营商转移电话号码
  • SS7 攻击：利用电信信令协议漏洞拦截短信
  • 恶意 App：Android 应用可获取短信读取权限
  • 实时钓鱼：攻击者实时中继 OTP 代码

建议：优先使用 FIDO2 > TOTP App > Push 通知 > SMS（最后手段）

4. Session 管理

认证成功后，需要一种机制来维持用户的登录状态。Session 是服务端状态管理方式，通过唯一的 Session ID 标识用户。

Set-Cookie: sid=; expires=... ──│ │ │ Session 存储选项: • 内存 (单服务器) • Redis / Memcached (分布式) • 数据库 (持久化)

4.2 Session ID 安全要求

要求原因推荐实现

4.3 Session 攻击

Session Fixation 攻击: 攻击流程: 1. 攻击者获取一个有效 Session ID (如访问网站得到 sid=EVIL123) 2. 攻击者诱导受害者使用这个 Session ID: - 发送链接: https://bank.com/login?sid=EVIL123 - 或通过 XSS 设置 Cookie 3. 受害者用 sid=EVIL123 登录 → Session 变为已认证状态 4. 攻击者使用同一 sid=EVIL123 → 获得受害者权限 ┌─────────┐ ┌──────────┐ ┌─────────┐ │ 攻击者 │ │ 受害者 │ │ 服务器 │ └────┬────┘ └────┬─────┘ └────┬────┘ │ │ │ │──获取 sid=X──────────────────→│ sid=X (未认证) │ │ │ │──诱导使用 sid=X→│ │ │ │ │ │ │─用sid=X 登录─→│ sid=X (已认证!) │ │ │ │──用 sid=X 访问──────────────→│ 验证通过 ✓ │ │ │ (攻击者获得受害者权限) 防御: 登录成功后 → 销毁旧 Session → 生成新 Session ID

5.2 JWT 常见攻击

攻击原理影响防御
Algorithm None将 alg 改为 "none"，移除签名绕过签名验证服务端白名单允许的算法
Algorithm Confusion将 RS256 改为 HS256，用公钥当 HMAC 密钥伪造有效 Token明确指定期望算法
弱密钥暴力破解HMAC 密钥太短/简单伪造任意 Token密钥 ≥ 256 bit 随机
Token 未验证 exp过期 Token 仍被接受永久有效的凭证始终验证 exp claim
敏感信息泄露Payload 存放密码/SSN信息泄露Payload 仅存 ID 和角色
Token 无法撤销JWT 无状态，无法主动失效被盗 Token 持续有效短过期 + Refresh Token + 黑名单
Algorithm Confusion 攻击详解

当服务器支持 RS256 (RSA) 和 HS256 (HMAC) 时：

  1. 服务器的 RSA 公钥是公开的
  2. 攻击者将 JWT header 中 alg 从 RS256 改为 HS256
  3. 用服务器的 RSA 公钥作为 HMAC 密钥对 payload 签名
  4. 如果服务器根据 header 中的 alg 选择验证方式，就会用"公钥"做 HMAC 验证 → 通过!

修复：服务端必须硬编码期望的算法，忽略 JWT header 中的 alg 声明。

5.4 JWT 最佳实践

JWT 安全使用指南
  • 算法：生产环境使用 RS256 或 EdDSA，避免 HS256 (除非严格的服务间通信)
  • 过期时间：Access Token 短命 (5-15 分钟)，配合 Refresh Token 使用
  • 密钥管理：HMAC 密钥 ≥ 256 bit；RSA 密钥 ≥ 2048 bit
  • Payload：不存敏感数据；包含 iss, sub, aud, exp, iat, jti
  • 验证：始终验证签名、算法、exp、iss、aud
  • 存储：浏览器端存于 HttpOnly Cookie (非 localStorage)
  • 撤销：使用 Token 黑名单 (Redis) 或短过期策略

RBAC 模型结构: 用户 (Users) 角色 (Roles) 权限 (Permissions) ┌─────────┐ ┌─────────┐ ┌──────────────────┐ │ alice │────────→│ admin │────────→│ user:read │ │ bob │────┐ │ │────────→│ user:write │ │ charlie │──┐ │ └─────────┘────────→│ user:delete │ └─────────┘ │ │ ┌─────────┐────────→│ post:read │ │ └──→│ editor │────────→│ post:write │ │ └─────────┘ │ post:delete │ │ ┌─────────┐────────→│ report:read │ └────→│ viewer │ └──────────────────┘ └─────────┘ 数据库设计: users: id, username, email roles: id, name, description permissions: id, resource, action user_roles: user_id, role_id (多对多) role_permissions: role_id, perm_id (多对多)

7.3 ABAC 策略示例

# ABAC 策略示例 (伪代码)
# 策略: 允许部门经理在工作时间访问本部门的员工数据

policy "department_manager_access":
  effect: ALLOW
  subjects:
    role == "manager"
  resources:
    type == "employee_record"
  actions:
    action in ["read", "update"]
  conditions:
    subject.department == resource.department  # 只能访问本部门
    AND environment.time BETWEEN "09:00" AND "18:00"  # 工作时间
    AND environment.ip_range in "10.0.0.0/8"  # 内网
    AND resource.classification != "top_secret"  # 非绝密
如何选择授权模型？
  • 简单应用 (几个角色)：RBAC 足够
  • 需要细粒度动态策略：ABAC (如 AWS IAM Policy)
  • 基于关系的权限 (谁是谁的朋友/成员)：ReBAC (如 Google Zanzibar → SpiceDB)
  • 通用建议：从 RBAC 开始，按需演进到 ABAC

8.1 mTLS (双向 TLS) 原理

普通 TLS vs mTLS: 普通 TLS (单向): Client ──────→ Server 验证服务器证书 ✓ 客户端身份未验证 ✗ mTLS (双向): Client ←─────→ Server 验证服务器证书 ✓ 验证客户端证书 ✓ 双方身份都确认 mTLS 握手流程: 1. Client → Server: ClientHello 2. Server → Client: ServerHello + Server Certificate 3. Server → Client: CertificateRequest (要求客户端证书) 4. Client → Server: Client Certificate + CertificateVerify 5. 双方验证对方证书 → TLS 连接建立 适用场景: • 微服务间通信 (Service Mesh: Istio, Linkerd) • 零信任网络架构 • 金融/支付系统 API • IoT 设备认证

    body_json = json.dumps(body, sort_keys=True, separators=(',', ':'))

    # 构造待签名字符串 (Canonical String)
    string_to_sign = f"{method}\n{path}\n{timestamp}\n{body_json}"

    # HMAC-SHA256 签名
    signature = hmac.new(
        api_secret.encode('utf-8'),
        string_to_sign.encode('utf-8'),
        hashlib.sha256
    ).hexdigest()

    # 返回需要添加的 HTTP Headers
    return {
        "X-API-Key": api_key,
        "X-Timestamp": timestamp,
        "X-Signature": signature,
    }

# 服务端验证
def verify_api_request(method, path, body, headers, api_secret):
    """服务端验证请求签名"""
    timestamp = headers.get("X-Timestamp")
    received_sig = headers.get("X-Signature")

    # 1. 验证时间戳 (防止重放攻击, 允许 5 分钟偏差)
    if abs(int(time.time()) - int(timestamp)) > 300:
        return False, "请求已过期"

    # 2. 重新计算签名
    body_json = json.dumps(body, sort_keys=True, separators=(',', ':'))
    string_to_sign = f"{method}\n{path}\n{timestamp}\n{body_json}"
    expected_sig = hmac.new(
        api_secret.encode('utf-8'),
        string_to_sign.encode('utf-8'),
        hashlib.sha256
    ).hexdigest()

    # 3. 恒定时间比较 (防止 Timing Attack)
    if hmac.compare_digest(expected_sig, received_sig):
        return True, "验证通过"
    return False, "签名无效"

from flask import Flask, request, session, jsonify
from argon2 import PasswordHasher
from functools import wraps
import secrets
import time
import redis

app = Flask(__name__)

rate_limiter = redis.Redis()

# === Rate Limiting ===
def rate_limit(max_attempts=5, window=300):
    """登录速率限制装饰器"""
    def decorator(f):
        @wraps(f)
        def wrapper(*args, **kwargs):
            ip = request.remote_addr
            key = f"login_attempts:{ip}"
            attempts = rate_limiter.get(key)

            if attempts and int(attempts) >= max_attempts:
                return jsonify({"error": "请求过于频繁，请稍后重试"}), 429

            result = f(*args, **kwargs)

            # 登录失败时增加计数
            if result[1] == 401:
                rate_limiter.incr(key)
                rate_limiter.expire(key, window)
            else:
                rate_limiter.delete(key)  # 登录成功清除计数

            return result
        return wrapper
    return decorator

# === 安全登录 ===
@app.route('/api/login', methods=['POST'])
@rate_limit(max_attempts=5, window=300)
def login():
    data = request.get_json()
    username = data.get('username', '').strip()
    password = data.get('password', '')

    # 1. 从数据库获取用户 (伪代码)
    user = db.get_user_by_username(username)

    # 2. 统一错误信息 (不泄露用户是否存在)
    error_msg = "用户名或密码错误"

    if not user:
        # 即使用户不存在，也执行一次哈希运算 (防止 Timing Attack)
        ph.hash("dummy_password_for_timing")
        return jsonify({"error": error_msg}), 401

    # 3. 验证密码
    try:
        ph.verify(user.password_hash, password)
    except Exception:
        return jsonify({"error": error_msg}), 401

    # 4. 检查是否需要 rehash (参数升级)
    if ph.check_needs_rehash(user.password_hash):
        user.password_hash = ph.hash(password)
        db.save_user(user)

    # 5. 重新生成 Session ID (防止 Session Fixation)
    session.clear()
    session.regenerate()
    session['user_id'] = user.id
    session['login_time'] = time.time()
    session['ip'] = request.remote_addr

    return jsonify({"message": "登录成功", "user": user.username}), 200

# === 授权装饰器 ===
def require_role(*roles):
    """基于角色的访问控制装饰器"""
    def decorator(f):
        @wraps(f)
        def wrapper(*args, **kwargs):
            user_id = session.get('user_id')
            if not user_id:
                return jsonify({"error": "未认证"}), 401

            user = db.get_user(user_id)
            if user.role not in roles:
                return jsonify({"error": "权限不足"}), 403

            return f(*args, **kwargs)
        return wrapper
    return decorator

# JWT 安全签发与验证
import jwt
import time
import uuid
from datetime import datetime, timedelta

# 配置
JWT_SECRET = secrets.token_hex(32)  # 256-bit 随机密钥
JWT_ALGORITHM = "HS256"  # 或使用 RS256 + RSA 密钥对
ACCESS_TOKEN_EXPIRE = 900  # 15 分钟
REFRESH_TOKEN_EXPIRE = 604800  # 7 天

def create_access_token(user_id: int, role: str) -> str:
    """创建短期 Access Token"""
    now = time.time()
    payload = {
        "sub": str(user_id),
        "role": role,
        "type": "access",
        "iat": now,
        "exp": now + ACCESS_TOKEN_EXPIRE,
        "jti": str(uuid.uuid4()),  # 唯一标识，用于黑名单
        "iss": "myapp.com",
        "aud": "myapp.com",
    }
    return jwt.encode(payload, JWT_SECRET, algorithm=JWT_ALGORITHM)

def create_refresh_token(user_id: int) -> str:
    """创建长期 Refresh Token"""
    now = time.time()
    payload = {
        "sub": str(user_id),
        "type": "refresh",
        "iat": now,
        "exp": now + REFRESH_TOKEN_EXPIRE,
        "jti": str(uuid.uuid4()),
    }
    token = jwt.encode(payload, JWT_SECRET, algorithm=JWT_ALGORITHM)
    # 将 Refresh Token 存入数据库 (支持撤销)
    db.store_refresh_token(user_id, payload["jti"], payload["exp"])
    return token

def verify_token(token: str, expected_type: str = "access") -> dict:
    """安全验证 Token"""
    try:

                "require": ["exp", "iat", "sub", "jti"],
                "verify_exp": True,
                "verify_iat": True,

import hashlib
import base64
import secrets
import urllib.parse

def generate_pkce_pair():
    """生成 PKCE code_verifier 和 code_challenge"""
    # code_verifier: 43-128 字符的随机字符串
    code_verifier = secrets.token_urlsafe(32)

    # code_challenge: S256 方法
    digest = hashlib.sha256(code_verifier.encode('ascii')).digest()
    code_challenge = base64.urlsafe_b64encode(digest).rstrip(b'=').decode('ascii')

    return code_verifier, code_challenge

常被忽视的安全要点
  • 密码重置：Token 必须一次性使用、短时效 (15分钟)、足够随机 (128-bit+)
  • 账户枚举：注册/登录/重置密码的响应不应泄露用户是否存在
  • 并发 Session：考虑是否允许多设备同时登录，以及新登录是否踢出旧 Session
  • 权限缓存：RBAC 角色变更后，确保 Session/Token 中的权限信息被刷新
  • 日志审计：记录所有认证事件（登录、失败、权限变更），但不记录密码
